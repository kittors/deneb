## 0. 先看这一页

**结论：做得到，难度不大。** 一台设备只要一个引擎，就能同时在两个局域网在线。这个引擎有一把密钥、一个地址、一个 UDP 端口、一条中转连接。隔离靠设备上的过滤和 WireGuard 自带的来源检查，不需要每个局域网一张网卡，也不需要每个局域网一段地址。原型在本机 Mac、hk-155、hk-spare、Windows 测试机上跑通了。✅

**推荐方案**（展开见 §3、§4）

1. **一个引擎服务所有局域网**：每个对端带着"和我共同在哪些局域网"的标签。加入、暂停、退出一个局域网只改表，不碰网卡、路由、端口和中转连接。（§3.1）
2. **桌面默认用内核网卡**：服务器、没有管理员权限或者和别的软件冲突时，改用用户态网络栈。两种模式共用同一个引擎。（§3.2）
3. **一台设备一个地址，所有局域网共用**：IPv4 在 `10.0.0.0/8` 里给每个部署随机取一个 `/16`，另外加 IPv6 ULA。**不用 `100.64.0.0/10`**：本机的 Tailscale 一看到别的网卡用这一段，就会改掉自己的路由。不按局域网切地址段。（§3.3）
4. **名字用 `设备.主人.deneb.internal`**：短名只有一台设备叫这个时才能用，有歧义就不猜，把候选列出来。（§3.4）
5. **隔离分四层**：控制面不下发、设备不转发、只放行开给这个局域网的服务、WireGuard 检查来源地址。任何一层单独都挡得住。（§3.5）
6. **中转直接复用 DERP**：用户现成的 derper 不用改。Deneb 发往公网的包要绑物理网卡，否则会被 Clash 绕到代理节点上。（§3.6、§3.7）

**实测结果**（本机测试时接的是手机热点，详见 §6）

| 要验证的事 | 结果 |
| --- | --- |
| 两个局域网同时在线 | ✅ 启动后 0.12 秒三台设备都经中转应答，0.63 秒换成直连：工作室的 box.lin 中位 67ms，周末联机的 nas.jie 中位 53ms。周末联机的 Windows 测试机打不了洞，一直经 hk-spare 中转。同一时间本机的 Tailscale 也连不上它，是热点 NAT 的限制 |
| 一个局域网暂停，另一个不受影响 | ✅ 周末联机暂停 10 秒，工作室没有多丢包，TCP 长连接没断；恢复后 0.12 秒就通了 |
| A、B 之间互相不可达 | ✅ 两个方向的借道攻击都不通。模拟 Mac 的过滤失灵后，对方的 WireGuard 照样把包丢掉 |
| 直连不通时走 hk-spare 中转 | ✅ 用的是现成的 derper，没改它的任何配置 |
| 切换表现 | 参数和 Tailscale 一样时（3 秒心跳、6.5 秒不信任），直连断后中断 6.2 秒，TCP 之后一直跟不上。改成 1 秒、2.5 秒后，中断 2.35 秒，TCP 很快恢复。两种参数下回到直连都不超过 0.72 秒，回切时不丢包 |
| 和 Clash 共存 | 不绑网卡时，所谓"直连"其实被 Clash 送到代理节点绕了一圈，延迟变成 5 倍左右。绑上物理网卡就正常 |
| 本机用内核网卡 | ✅ 一张 utun、一条 `10.86.0.0/16` 路由、一个只管 `deneb.internal` 的 DNS 文件：普通程序不设代理就能访问三台设备；Mac 上普通程序开的服务按局域网放行；Clash 劫持全部 DNS 的情况下名字照样解析；Tailscale 的路由和 SSH 心跳全程没变；撤销后路由表和 DNS 配置与开始前一致。期间经 Clash 访问外网有两段超时，排查后判断不是冲突，最可能是 Clash 节点（Hysteria2，跑在 UDP 上）自身的波动（§6.9） |

**对产品的含义**：场景 3 能兑现。暂停、恢复几乎是瞬间的，可以照 demo 做。"直接连上 / 经中转"会在几秒内来回变，画面换状态要防抖。Clash 用户不用做任何设置。手机系统只给一个 VPN 位置，Deneb 和 Clash 类应用没法同时开，这一条还没有解法（§3.7 第 5 条）。

**还没验证**：Windows 和 Linux 上的内核网卡、两台都在 NAT 后面的设备跨网直连（这次测到的 Mac 和 Windows 是同一个家庭网络）、多中转站、手机。见 §7。

## 1. 要验证的是什么

"一台设备再拖一次进第二个局域网"落到技术上，是下面 8 条要求：

| 编号 | 要求 | 出处 |
| --- | --- | --- |
| Q1 | 同时在线：在两个局域网里都能收发，没有"切换" | DESIGN §6.4，调研 §5.1 |
| Q2 | 互不打扰：加入、暂停、退出一个局域网时，另一个局域网里正在用的连接不断 | 场景 3 第 2 条"周末联机已暂停，其他照常" |
| Q3 | 地址不打架：两个局域网的设备地址不冲突，也不和本机的 Tailscale、Clash、运营商地址冲突 | 调研 §0 第 1 条 |
| Q4 | 名字分得清：两个局域网里都有叫 box 的设备时，能分开叫到 | 调研 §6.4 第 8 条 |
| Q5 | 不串门：A 局域网的人看不到 B 里有什么，也不能借我的设备摸到 B | 本次任务 |
| Q6 | 先通后快：直连优先，连不上自动走中转站；中转站可以复用，包括用户自己的 DERP | 调研 §1.4 |
| Q7 | 和代理软件共存：本机开着 Clash TUN 也能用 | 调研 §5.7、§6.4 第 7 条 |
| Q8 | 手机上也成立 | 本次只论证，没有实测 |

| 机器 | 原型里的身份 | 系统 | 网络 |
| --- | --- | --- | --- |
| 本机 Mac | `mac.me`，同时在两个局域网 | macOS 27.0.1，arm64 | 测试时换到了手机热点。这个网络的 NAT 对不同目的地会换用不同的公网地址和端口：STUN 看到 220.205.x.x:61690，hk-155 看到另一个 220.205.x.x:62822。另装有 Clash Verge（mihomo）的 TUN 模式和 Tailscale 1.102.4 |
| hk-155 | `box.lin`，局域网 A「工作室」 | Debian 12，x86_64 | 公网 103.42.x.x，地址直接在网卡上 |
| hk-spare | 中转站；另跑 `nas.jie`，局域网 B「周末联机」 | Debian 12，x86_64 | 公网 43.255.x.x。derper 1.102.3，TLS 33443，STUN 3478，没开 `--verify-clients`。原型只是它的普通客户端 |
| Windows 测试机 | `box.jie`，局域网 B「周末联机」 | Windows 11 家庭版 | Wi-Fi 192.168.1.17，家用路由器后面，出口 36.159.x.x（中国移动），路由器会改端口（41702 变成 31902）。系统防火墙开着，装着 Tailscale |

本机的现状决定了"共存"要怎么做：

- **Clash TUN**（utun4，198.18.0.1）：用 `1/8`、`2/7`、`4/6`、`8/5`、`16/4`、`32/3`、`64/2`、`128/1` 这 8 条路由，接管了除 `0/8` 以外的全部 IPv4。它还劫持所有 DNS：分别向 114.114.114.114、1.1.1.1、223.5.5.5 查 `derp.example.com`，得到的都是假地址 198.18.3.233，真实地址其实是 hk-155。✅
- **Tailscale**（utun8）：装了一条 `100.64.0.0/10` 指向自己。它比 Clash 的 `64/2` 更具体，所以 Tailscale 的流量绕开了 Clash。它的 DNS 是关着的；它的设备名经系统解析，同样被 Clash 换成了假地址 198.18.3.234。✅
- **Windows 上的 Tailscale**：按对端一条一条装 `/32` 路由，一共 10 条，没有整段 `/10`。✅ Tailscale 源码里写了原因：macOS 和 Android 默认只装一条整段路由，因为在这两个系统上改隧道配置会打断现有连接（macOS 上 Chrome 尤其明显；Android 要重建 VPN 接口，长连接会断）；只有别的网卡也在用这段地址时，才改成逐个 `/32`。[S1]
- **中转站域名**：`derp.example.com` 解析到 hk-155，hk-155 上也跑着同样配置的 derper。原型按 IP 直接连 hk-spare，TLS 仍然校验这个域名。

## 3. 技术路线比较

### 3.1 每个局域网一张网卡，还是一张网卡分局域网

| | 甲：每个局域网一张网卡 | 乙：一张网卡，按局域网给对端打标签（推荐） |
| --- | --- | --- |
| 做法 | 每个局域网一套独立的 WireGuard（或一个 tailscaled），各有自己的密钥、UDP 端口、中转连接和虚拟网卡 | 一台设备一个引擎：一把密钥、一个 UDP 端口、每个中转站一条连接、一张网卡。每个对端带"和我共同在哪些局域网"的标签，隔离靠引擎里的过滤 |
| 好处 | 局域网之间天然分开，崩一个不影响另一个；桌面端拿现成的 WireGuard 或 Tailscale 就能拼出来 | 手机上做得到；加入、暂停、退出局域网只改引擎里的表，不碰网卡、路由、密钥和端口（Q2）；同在两个局域网的对端只有一条隧道；打洞、心跳、中转连接都只做一份 |
| 风险 | **手机做不到**：Android 同一时间只允许一个 VPN 接口 [D3]；iOS 一个应用只能有一个 VPN 连接，所以 ZeroTier 的 iOS 版同一时间只能连一个网络 [D4]。地址冲突也没解决，几张网卡共用一张路由表。Windows 上每张网卡都会出现在"网络连接"里，各自弹一次网络类型。耗电和服务器连接数翻倍。Tailscale #183 里有人同时跑两个 tailscaled，结果两边都不稳 [G1] | 隔离是我们自己写的代码，写错就会串门，必须有测试守住（原型的测试见 §6.4）。一把密钥意味着两个局域网的人能认出这是同一台设备；名字本来就看得出，影响小。真要分开，可以每个局域网用不同的密钥，代价是多一条连接 |
| 工作量（粗估） | 桌面 1–2 周能跑起来；手机无解 | 在 Tailscale 开源客户端的底层上改：引擎 3–5 周，控制面按局域网下发设备表 2–3 周 |

**选乙。** 甲只适合当桌面端的临时绕法。

### 3.2 内核 TUN，还是用户态网络栈

| | 内核 TUN | 用户态网络栈（类似 tsnet、Tailscale 的 userspace-networking） |
| --- | --- | --- |
| 做法 | 系统里多一张虚拟网卡（macOS 网络扩展、Windows Wintun、Linux 的 /dev/net/tun、iOS 的 NEPacketTunnelProvider、Android 的 VpnService），再装路由和分域 DNS | TCP/IP 协议栈（gVisor）跑在 Deneb 进程里，不建网卡，不改路由和 DNS。本机程序经 Deneb 的本地代理（SOCKS5）或端口映射出去；别人连进来时，由 Deneb 转给本机对应的服务 |
| 好处 | 所有程序直接能用，远程桌面、共享文件夹、浏览器都不用另外设置；别人连我开的服务也不用额外转发 | 不要管理员权限，不改系统，和 Clash、Tailscale 互不干扰（原型实测）；装在服务器、NAS、容器里，或者嵌进别的应用都方便；只有"开了的服务"才进得来，和 DESIGN 里的"服务"一一对应 |
| 风险 | 要权限、签名和上架审核（macOS 网络扩展、Windows 驱动）；改路由和 DNS 会和代理软件、别的 VPN 打架（§3.7）；在 macOS、Android 上改隧道配置会打断现有连接 [S1] | 普通程序不会自己走代理，普通人也不会设置；吞吐低一些；局域网广播类功能（比如游戏发现局域网房间）用不了 |
| 工作量（粗估） | 各平台的路由和 DNS 管理可以复用 Tailscale 开源代码；macOS 网络扩展打包签名 2–4 周，Windows 1–2 周 | 1–2 周，可参考 Tailscale 现成的 userspace-networking 和 SOCKS5 |

**两种都要，用同一个引擎。** 桌面默认用内核 TUN；没有权限、装在服务器或 NAS 上、或者检测到冲突时，改用用户态。原型只做了用户态，这样不用改本机的系统设置。隔离、路径、名字的逻辑都在引擎里，换成内核 TUN 时不用改。

### 3.3 地址怎么分（100.64.0.0/10 怎么切：结论是不用它）

| | 按局域网切地址段 | 一台设备一个地址（推荐） | 每台设备给对端另编本机地址 |
| --- | --- | --- | --- |
| 做法 | 每个局域网分一段（比如 /20），设备在每个局域网各有一个地址 | 控制面给每台设备一个地址，进几个局域网都用这一个。隔离不靠地址段，靠过滤 | 允许对端的真实地址重复；本机给"局域网 × 设备"各编一个本机不冲突的地址，引擎做一对一地址转换 |
| 好处 | 看地址就知道是哪个局域网；一个局域网一条路由 | 简单；地址稳定，"复制地址"给谁都一样；进第二个局域网不新增地址、不改路由（Q2）；同在两个局域网的对端只有一个地址 | 在本机永远不冲突；自建和公共几个控制面混着用也不怕 |
| 风险 | 段数有限（/10 里的 /20 只有 1024 段），局域网的数量却没有上限；设备每进一个局域网就多一个地址、多一条路由，在 macOS、Android 上会打断现有连接 [S1]；两个局域网撞了段，只能整个局域网换号 | 一个部署内要全局唯一，地址池有上限；自建和公共两个部署的设备可能撞号；地址段要避开本机已有的网段（见下面第 6 条） | 同一台设备在不同人的电脑上地址不一样（只用名字时感觉不到）；地址转换要处理校验和、ICMP 等细节；排查问题时容易糊涂 |
| 工作量（粗估） | 1 周 | 1–2 周（含冲突检查） | 2–3 周 |

**推荐：一台设备一个地址，不按局域网切段，也不用 100.64.0.0/10。** 细则如下：

1. 每台设备一个 IPv4 和一个 IPv6，在它所在的所有局域网里都一样。原型就是这么做的：Mac 在两个局域网里都是同一个地址（用户态那几轮是 100.86.0.1，内核网卡那一轮是 10.86.0.1）。✅
2. **不用 `100.64.0.0/10`。** 起初打算从这一段取，做内核网卡测试前读 Tailscale 源码时改掉了，原因有三：
   - macOS 上的 Tailscale 应用只要发现别的网卡有这一段的地址，就会把自己那条整段路由换成逐台设备的 `/32`，并重新配置网络扩展；它自己的注释说，这样可能打断现有连接 [S1] [S5]。也就是说，Deneb 用这一段会扰动用户本机的 Tailscale。
   - Linux 上的 Tailscale 会装一条防火墙规则，丢弃不是从它自己网卡进来、来源地址又在这一段的包 [S6]。Deneb 的流量用这一段，在装了 Tailscale 的 Linux 上会被直接丢掉。
   - 阿里云 ECS 默认的 DNS 是 100.100.2.136 和 100.100.2.138 [D6]，运营商级 NAT 也用这一段。
3. **IPv4 用 `10.0.0.0/8` 里的一个 `/16`**，每个部署随机选（原型用 `10.86.0.0/16`），避开 `10.0.x`、`10.1.x`、`10.10.x` 这类家用路由器和公司常用的网段。一个 `/16` 约 6.5 万个地址，自建和早期够用；公共服务做大以后，要么一个租户一个 `/16`，要么改成以 IPv6 为主。
4. IPv6 用随机生成的 ULA `/48`（RFC 4193 规定的 40 位随机 ID），不同部署撞上的概率可以忽略。
5. 路由：
   - macOS、iOS、Android 装一条覆盖整个 `/16` 的路由，进出局域网都不用改，不会打断现有连接。
   - Windows、Linux 按对端装 `/32`，改路由代价小；Tailscale 在 Windows 上就是这么做的。
6. 冲突检查：启动和换网时读一遍本机的网卡地址和路由表（原型的 `-preflight` 就是做这一步）。
   - 这个 `/16` 只能被默认路由或代理软件的大路由覆盖（本机是 Clash 的 `8/5`）。Deneb 的 `/16` 比它们具体，所以只接管自己的流量。✅
   - 10.x 是私有地址，用户的公司或家庭网络可能正好用到同一段。撞上时换一个 `/16`，或者改用用户态，并用一句话提示。
7. Deneb 的 DNS 服务地址放在自己的 `/16` 里（原型是 `10.86.0.53`），不用 100.100.100.100，那个被 Tailscale 占着。

### 3.4 名字怎么区分（同名设备）

| | 用局域网名做后缀，如 `box.studio` | 用主人做后缀，如 `box.lin`（推荐） | 只用短名 `box` |
| --- | --- | --- | --- |
| 好处 | 和"它在哪个局域网"的直觉一致 | 一台设备只有一个正式名字，和"一台设备一个地址"一致；同名的设备一定属于不同的人（同一个人有两台同名设备时，第二台自动加 -2） | 最短 |
| 风险 | 同一台设备进了两个局域网就有两个名字；局域网改名，所有名字都跟着变；中文局域网名要转拼音或 punycode；同一个局域网里两个人的同名设备还是分不开 | 每个人要有一个英文短名，可以取自邮箱或注册时自动生成，在"更多"里能改 | 一出现同名就分不开 |

**推荐：**

- 正式名用 `<设备>.<主人>.deneb.internal`。`.internal` 是 ICANN 在 2024 年专门保留给私用的顶级域，永远不会被公网注册 [D7]。
- 短名 `box` 只在"我看得到的设备里只有一台叫 box"时能用；有歧义就不猜，直接拒绝并列出候选。原型实测 ✅：
  - 在 Mac 上查 `box`，返回"有 2 台：box.lin（工作室）、box.jie（周末联机）"。
  - Windows 只看得到自己的局域网：查 `box` 得到的就是它自己；查 `box.lin` 返回"不存在"，因为它根本不知道有工作室。
- 界面上永远写清"谁的什么设备 · 在哪个局域网"，比如"阿杰的 box · 周末联机"。"复制地址"复制的是正式名。
- DNS 只接管 `deneb.internal` 这一个后缀，别的查询一概不碰。具体做法：macOS 用网络扩展的 matchDomains（原型用的是等效的 `/etc/resolver/deneb.internal`），Windows 用名称解析策略表（NRPT），Linux 用 systemd-resolved 的 `~deneb.internal`。macOS 上已实测通过（§6.8）✅；Windows 和 Linux 没测。
- 用户态模式下，名字在 Deneb 进程里解析（SOCKS5 远程解析），不经过系统 DNS，所以不受 Clash 假地址的影响。原型实测 ✅：在开着 Clash TUN 的本机上，用 `curl --socks5-hostname 127.0.0.1:41080` 访问 `http://box.lin.deneb.internal/` 和 `http://box.jie.deneb.internal/`，两个都能直接打开。

### 3.5 访问控制怎么按局域网隔离

"A 局域网的人不能借我的设备摸到 B"拆成四层。任何一层单独都挡得住，叠在一起，是为了防某一层写错：

1. **看不见（控制面）**：每台设备只拿到"和它至少同在一个局域网"的设备清单，而且只告诉它双方共同在哪些局域网。原型里，hk-155 的清单里只有 Mac，标签也只有"工作室"。它不知道 Mac 还在"周末联机"里，更不知道 Windows 测试机的存在。✅
2. **不转发（设备上的过滤）**：引擎只收目的地址是自己的包，只发源地址是自己的包。别人发来想借道的包，在入口就被丢掉。就算系统开了 IP 转发（装了 Docker 的 Linux 默认就是开的），借道的包被系统转回网卡时，源地址不是自己，出口这一关也会丢。
3. **只放行开了的服务（设备上的过滤）**：有新连接进来时，先查对方和我共同在哪些局域网，再看我对这些局域网开了哪些服务。工作室的人只能用我开给工作室的服务。我自己发起的连接，回包照常放行。
4. **加密路由（WireGuard 自带）**：每个对端只能用它自己的地址发包（AllowedIPs 就是它自己那一个 `/32`）。就算 Mac 的过滤坏了，把 hk-155 的包转给了 Windows，Windows 一看来源地址不是 Mac 的，也会丢掉。

剩下的风险在应用层。如果我把一个代理，或者带端口转发的 SSH 开给了工作室，工作室的人就能通过它访问我能访问的一切，包括周末联机。这和把电脑借给别人用是一回事，网络层挡不住。界面上开"命令行"这类服务时，要提示一句。

### 3.6 直连优先、中转兜底怎么复用

- **沿用 Tailscale 的做法**：一开始就经中转连上，同时打洞；打通了就悄悄换成直连；直连没回应了就退回中转，并且继续尝试打洞（调研 §1.4）。
- **DERP 按设备公钥转发，不认识局域网**：所以一台设备一条中转连接，就能服务它所在的所有局域网。Tailscale 自己的 derper 不用改，直接就能当 Deneb 的中转站。原型直连的就是 hk-spare 上现成的 derper。✅
- **一对设备只有一条路径**：同在两个局域网的对端，打洞和心跳只做一份。
- **中转站跟着局域网走**（DESIGN §6.4"中转站对整个局域网生效"）：设备对它所在每个局域网指定的中转站各保持一条连接；发给某个对端时，走对方常驻的那个中转站。原型只有一个中转站，这一条没测。⚠️
- **时间参数**：Tailscale 每 3 秒心跳一次，6.5 秒没收到回应就不再信任直连 [S2]。原型默认用同样的数，另外测了更激进的 1 秒、2.5 秒（§6.2）。建议心跳只在有流量时跑（Tailscale 就是这样），这样激进参数的耗电代价才可以接受。

### 3.7 和 Clash TUN（以及本机的 Tailscale）共存

1. **设备之间的流量**（目的地址在 Deneb 的 `/16` 里）：装比 Clash 更具体的路由，自然就绕开了 Clash。本机的 Tailscale 就是这么做的（它的 `/10` 比 Clash 的 `64/2` 更具体）。✅ 已实测：Deneb 的 `10.86.0.0/16` 比 Clash 的 `8/5` 更具体，去这一段的流量走 Deneb 的网卡，其他流量照旧走 Clash（§6.8）。
2. **Deneb 自己发往公网的包**（打洞用的 UDP、STUN、连中转站的 TLS）：把套接字绑到物理网卡上（macOS 用 IP_BOUND_IF，Windows 用 IP_UNICAST_IF，Linux 用 SO_BINDTODEVICE），不让 Clash 在中间转一道。实测这一条决定了"直连"是不是真的直连（§6.5）。如果绑网卡后连不上中转站，再退回走系统路由（也就是经 Clash 代理），保证至少还能经中转。
3. **DNS**：只接管 `deneb.internal`。DNS 服务地址放在 Deneb 的 `/16` 里，查询走 Deneb 的网卡，Clash 看不到。如果检测到 Clash 的假地址（198.18 段），就用一句话告诉用户在 Clash 里加哪一行（在 `fake-ip-filter` 里加 `+.deneb.internal`）；Deneb 自己不去改 Clash。实测在本机，这类查询全部到了 Deneb，Clash 没有插手，所以用不上这条提示（§6.8）。
4. **地址避开 `198.18.0.0/15`**：Clash 的假地址就在这一段（本机正在用 198.18.x），Surge 等软件的虚拟网卡也在这里。
5. **手机**：系统只有一个 VPN 位置，Deneb 和 Clash 一类的应用没法同时开（调研 §5.7 里 iOS 用户就是这样来回切的）。出路有两条：和代理软件合作（Surge 6 已经内置了 Tailscale，调研 [V14]）；或者在 Android 上由 Deneb 提供本地代理，让代理软件转发过来。先记为未决。

完整的共存做法，以及"Deneb 有没有拖慢 Clash"的排查依据，见 §6.9。

## 4. 推荐方案

```
一台设备 ＝ 一把密钥
          ＋ 一个地址（部署的 /16 里一个 IPv4，加一个 IPv6）
          ＋ 一个引擎（一个 UDP 端口，每个中转站一条连接）
          ＋ 一张内核网卡（桌面默认），或用户态网络栈（服务器、没权限、有冲突时）

引擎里只有三张表，都由控制面下发：
  对端表：每个对端的公钥、地址、和我共同在哪些局域网
  开放表：我对每个局域网开了哪些服务
  中转表：每个局域网用哪些中转站

收包：解密（WireGuard 核对来源地址）
      → 目的地址是我吗
      → 是我发起的连接的回包吗；不是的话，我对共同的局域网开了这个服务吗
发包：源地址是我吗 → 对方在我看得见的局域网里吗 → 有直连走直连，没有就走中转

加入、暂停、退出一个局域网 ＝ 改这三张表。网卡、路由、密钥、端口、中转连接都不动。
```

工作量粗估：按一名熟悉 Go 和 WireGuard 的工程师计，在 Tailscale 开源客户端的底层上改，不从零写。

| 模块 | 粗估 |
| --- | --- |
| 引擎支持多局域网：对端标签、过滤、暂停和恢复 | 3–5 周 |
| 控制面：按局域网下发设备表、地址分配、冲突检查 | 2–3 周 |
| 名字：正式名和短名规则，三个桌面平台的分域 DNS | 2 周 |
| 中转站按局域网分组 | 1–2 周 |
| 和 Clash 共存：绑物理网卡、检测和提示 | 1 周，另加兼容测试 |
| 内核网卡：macOS 网络扩展打包签名 / Windows | 2–4 周 / 1–2 周 |
| 手机（iOS、Android） | 各 4–6 周，另算 |

许可证：Tailscale 客户端是 BSD-3，wireguard-go 是 MIT，gVisor 是 Apache 2.0，都允许商用改造，要保留版权声明。✅

## 5. 原型

`poc/multi-lan/`，Go 写的，约 2900 行，另有 141 行过滤规则的单元测试。所有机器上跑的是同一个程序 `deneb-poc`：

```
              ┌────────────── 本机 Mac：mac.me（100.86.0.1） ─────────────┐
 本机程序 ──► │ SOCKS5 127.0.0.1:41080：名字在进程里解析                  │
              │ gVisor 用户态网络栈（一个地址）                            │
              │ 过滤层：不转发、按局域网放行服务、放行回包                  │
              │ wireguard-go（一把密钥，3 个对端，分属 2 个局域网）         │
              │ 小号 magicsock：1 个 UDP 端口 + 1 条 DERP 连接，负责探测和切换 │
              └──────┬────────────────────┬─────────────────────┬────────┘
               直连 UDP              直连 UDP            经中转（打不了洞）
                     ▼                    ▼                     ▼
        box.lin（hk-155）       nas.jie（hk-spare）       box.jie（Windows）
           「工作室」              「周末联机」              「周末联机」
                     └── 所有设备都连 hk-spare 上现成的 derper，用于中转和交换地址 ──┘
```

- **控制面**：没有服务器。`gen` 子命令按 `topology.json` 给每台设备生成配置，里面只有和它同在某个局域网的对端，扮演控制面下发设备表。
- **地址**：用户态那几轮用 `100.86.0.0/16`，内核网卡那一轮改用 `10.86.0.0/16`（原因见 §3.3）。
- **测试用的服务**：每台设备在隧道地址上开 4 个小服务。UDP 回显 :7 用来测延迟，网页 :80 会报"我是谁、你是谁、我们共同的局域网"，计时流 :7000 每 100ms 发一行，测速 :9000。
- **控制接口**：只听本机回环。能查状态、ping、模拟 UDP 被封、暂停和恢复局域网、伪造来源注入。

和推荐方案相比做了这些简化：

- 内核网卡只在本机 Mac 上做了（§6.8），远端三台都在用户态。
- 没有真正的控制面服务器。
- 只有 IPv4。
- 只用一个中转站。
- 探测消息直接用 WireGuard 密钥加密（Tailscale 用单独的 disco 密钥）。
- 心跳一直在跑，不管有没有流量。

## 6. 实测结果

§6.1 到 §6.6 在 2026-11-07 傍晚测得，本机接的是手机热点，并开着 Clash TUN。§6.8 是当晚 20 点后在家里 Wi-Fi 上测的。除 §6.5 外，原型都绑在 en0 上。原始数据在 `poc/multi-lan/results/raw/`，这个目录不进仓库。

### 6.1 两个局域网同时在线 ✅

启动后立刻每 100ms 同时 ping 三台设备，各发 100 个（18:38）：

| 对端 | 局域网 | 第一次应答 | 换成直连 | 之后的延迟（中位 / 95 分位） | 丢包 |
| --- | --- | --- | --- | --- | --- |
| box.lin（hk-155） | 工作室 | +0.12 秒，经中转 | +0.63 秒 | 67 / 83 ms | 2/100 |
| nas.jie（hk-spare） | 周末联机 | +0.12 秒，经中转 | +0.63 秒 | 53 / 73 ms | 2/100 |
| box.jie（Windows） | 周末联机 | +0.12 秒，经中转 | 没有 | 648 / 1362 ms（经中转） | 0/100 |

对照数据：

- **裸网络延迟**：本机经 en0 直接 ping 两台服务器（18:47），hk-155 平均 46ms，hk-spare 平均 49ms。
- **Windows 为什么一直走中转**：本机这时在手机热点上，热点的 NAT 对不同目的地会换地址和端口，Windows 那边家用路由器的 NAT 也会改端口。两边都这样就打不了洞。同一时间本机 Tailscale 到这台 Windows 也提示 "direct connection not established"，走官方香港中转，延迟 400–520ms。之前本机还在 Wi-Fi 上时，Tailscale 到它是直连的。
- **中转延迟波动大**：经 hk-spare 中转的延迟在整个测试期间中位数在 300–650ms 之间变化，跟运营商到 hk-spare 机房的线路状况有关。18:16 那次，本机直接 ping hk-spare 平均就有 196ms，最高 905ms。
- **直连的少量丢包来自热点上行**：本机发出 300 个，hk-155 收到 296 个；hk-155 回的 296 个，本机全部收到。

资源占用：本机这个进程同时在两个局域网、连着三个对端，只开了 1 个 UDP 端口和 1 条到中转站的 TCP 连接（lsof 核对）。✅

### 6.2 切换：直连断了，然后又恢复

做法：对 box.lin 每 100ms 发一个 ping，同时挂一条 TCP 长连接。第 10 秒起丢弃本机和 box.lin 之间的所有 UDP，模拟网络突然开始封 UDP。这是在原型里丢包，没有改防火墙，两端都不会收到通知。第 30 秒恢复。

| 参数 | 直连断后多久开始走中转 | ping 的中断 | TCP 长连接 | 恢复后回到直连 |
| --- | --- | --- | --- | --- |
| 心跳 3 秒 / 6.5 秒不信任（和 Tailscale 一样） | +6.3 秒 | 6.2 秒（丢 62 个） | 没断，数据不缺；先卡 6.6 秒，之后在中转上一直跟不上，每 2 秒只到 2–8 行（正常是 20 行），回到直连后积压的 244 行一次到齐 | +0.72 秒，回切时不丢包 |
| 心跳 1 秒 / 2.5 秒不信任 | +2.5 秒 | 2.35 秒（丢 24 个） | 没断；卡 2.6 秒，之后在中转上满速 | +0.61 秒，回切时不丢包 |

- 同样参数下又重复了一次（18:40）：中断 6.27 秒，回到直连用 0.69 秒。
- 这几轮里中转的中位延迟是 58–167ms，直连是 67–71ms。
- 中断时长基本等于"多久收不到回应就不再信任直连"这个时长。断的时间越长，TCP 的重传间隔退避得越大，之后就越难追上；所以 6.5 秒的那一轮在中转上一直跟不上，2.5 秒的那一轮很快恢复。
- 稳态下 TCP 走中转是能跟上的：一条走中转的计时流，20 秒收到 189 行，最长停顿 645ms。
- 在热点这种丢包多的线路上，nas.jie 有两次因为连续收不到心跳回应，短暂退到中转，分别是 0.07 秒和 2.5 秒。期间流量改走中转，当时正在进行的下载没有中断。参数越激进，这种短暂退回会越多，但不会造成断线。界面上"直接连上 / 经中转"换状态要防抖。

### 6.3 暂停一个局域网，另一个照常 ✅

对应场景 3 里的开关。两个局域网同时有流量时，暂停周末联机 10 秒再恢复（18:50）：

| | 暂停的 10 秒里 | 恢复后 |
| --- | --- | --- |
| 工作室 box.lin | 照常。丢包 4/300，和平时一样，最长中断 0.1 秒；TCP 长连接最长停顿 227ms，没断 | — |
| 周末联机 box.jie、nas.jie | 按设计不可达，名字也查不到 | 0.12 秒后应答；nas.jie 一恢复就是直连 |

### 6.5 和 Clash TUN 共存

同一时刻，把本机节点分别以两种方式启动（18:38）：

| | 绑物理网卡（`-bind-if en0`） | 不绑，走系统路由，也就是经过 Clash |
| --- | --- | --- |
| STUN 看到的本机公网地址 | 手机热点运营商的地址 220.205.x.x | Clash 代理节点的地址 104.194.x.x |
| box.lin（hk-155） | 直连，中位 67ms | 显示"直连"，实际是经代理节点绕了一圈，中位 315ms |
| nas.jie（hk-spare） | 直连，中位 53ms | 同上，中位 320ms |
| box.jie（Windows） | 打不了洞，经中转 | 借代理节点的 NAT 打通了，中位 310ms |
| 名字解析 | 在进程里解析，不受 Clash 假地址影响 | 同左 |

结论：

- 不绑网卡，"直接连上"会悄悄变成"经你的代理服务器"：延迟变成 5 倍左右，还消耗代理流量，界面上显示的状态也是错的。所以 Deneb 发往公网的包必须绑物理网卡。
- 反过来看，用户自己的代理服务器在某些网络下打洞反而更容易。将来可以考虑让用户把自己的服务器明确地"拖进来当中转站"，而不是让它在暗中起作用。

### 6.7 原型踩到的坑（对正式实现有用）

1. **wireguard-go 用户态栈的 ICMP 读接口会漏读**：刚握完手、回包扎堆到达之后，后面的回包都读不出来，表现成假丢包。WireGuard 的收包计数显示回包其实到了。测量改用 UDP 回显后就正常了。⚠️ 具体机制没有查到底，推断是读接口在回包扎堆时漏掉了到达通知。
2. **对端重启后握手卡 5 秒**：对端还信任着旧的直连路径，会把握手回包直接发过来。如果把这种来源不明的包丢掉，WireGuard 就要等 5 秒才重试握手。修法有两步：配置里已知的地址要登记到"按来源找对端"的表里；来源不明的包交给 WireGuard 自己去认证。关掉漫游以后这样做是安全的，wireguard-go 不会因此改写对端的端点 [S4]。
3. **新对端上线时要立刻探测**：不要等第一次心跳。第 2、3 两处一起改完后，box.lin 从启动到第一次应答由 3.4 秒降到 0.12 秒，到直连由 3.4 秒降到 0.63 秒。
4. **"多久不信任直连"这个时长决定中断长度**：它还影响 TCP 能不能顺利恢复（§6.2）。
5. **macOS 的 utun 读写要在包前留 4 字节**，给协议族头用。用户态栈不在乎这个；换成内核网卡时，读包偏移写成 0 会越界。
6. **地址段别用 100.64/10**：这是做内核网卡测试前读 Tailscale 源码时发现的（§3.3），在动本机之前就改掉了。

### 6.9 那两段外网超时的排查

起因是 §6.8 里经 Clash 访问 Google 的两段超时：一段约 20 秒，出现在从 Windows 拉 20MB 文件之后；一段约 1 分钟，出现在暂停工作室之后。要回答的是：这是不是 Deneb 引擎和 Clash TUN 冲突造成的。

**先只读核对每一个可能冲突的地方**（都没有改本机网络，也没碰 Clash 的配置）：

| 方向 | 查到的事实 | 结论 |
| --- | --- | --- |
| 路由优先级 | 新增的路由只有 `10.86.0.0/16` 一条；访问 Google 时 Clash 返回 198.18 段的假地址，这个地址仍走 Clash 的 utun4；拆掉前后路由表一致（§6.8） | 不冲突 |
| DNS 劫持 | `/etc/resolver` 只多了 `deneb.internal` 一项；Google 照旧由 Clash 解析。14 次失败里，13 次是等满 4 秒超时，1 次在 0.65 秒时连接被断开；解析失败的话会立刻报错，不是这种表现 | 不冲突 |
| UDP 端口 | 本机 41701 只有 Deneb 在用（系统 UDP 套接字列表）；Clash 的代理连接用它自己的端口 | 不冲突 |
| 出站绑定和 en0 | Deneb 的 UDP 和中转 TLS 都绑在 en0，Clash 的出站也走 en0（`auto-detect-interface`），是各自独立的套接字。家里路由器给 Deneb 映射的公网地址和端口全程没变；Deneb 到中转站的连接一次没断 | 不冲突 |
| MTU | Deneb 网卡的 1280 只作用于发往 10.86 段的包；Clash 网卡是 9000，en0 是 1500，都没变 | 不冲突 |
| utun 序号 | Deneb 新建的是 utun10，Clash 是 utun4，Tailscale 是 utun8，没有重号；拆掉后 utun 列表恢复原样 | 不冲突 |

**Clash 这边的情况**：通过 mihomo 的本地控制套接字只读查询（只用了查询接口，没有切节点、触发测速或重载）：

- Google 的流量走"🔍 Google → 🚀 节点选择 → 美西-Hy2"。这两个都是手动选择的分组，不会自动换节点，所以那两段时间里一直走的是同一个节点。
- 美西-Hy2 用的是 Hysteria2 协议，跑在 UDP（QUIC）上。
- mihomo 的日志没有存盘，那个节点今天也只在上午有两次测速记录，查不到 20:23 前后它的状态。

**同一时段的网络状况**：

- 家里宽带出境的 UDP 丢包严重：hk-155 发回本机的 UDP 丢了约 20%（§6.8）。
- 三台远端到本机的直连，在整个测试期间都频繁短暂退回中转，并不只在那两段时间里。
- 网卡出现之前的 10 分钟里，同样的 Google 超时也出现过 3 次。

**复现**（21:38–21:46，同一个家里 Wi-Fi）：

- 用户态模式，不建网卡、不改路由，其他和 §6.8 一样：本机节点绑 en0，三台远端照常运行。
- 每秒探测一次经 Clash 访问 Google（走美西-Hy2）和直连国内网站，同时通过本地控制套接字只读接收 mihomo 的警告级日志。
- 把两个可疑操作各做两次，每次之后留 60 秒观察：
  - A：经 Deneb 从 Windows 拉 20MB，速度 80–115 Mbps；
  - C：暂停工作室 10 秒再恢复。
- 对照 B：不经 Deneb，用局域网直接 scp 拉同样的 20MB。scp 走的是系统内核的 TCP，正好也覆盖了内核网卡模式下"系统 TCP 大流量过 Wi-Fi"这种情况。

| 操作（各两次） | 之后 60 秒内 Google 失败 | 之后 60 秒内国内网站失败 | mihomo 警告 |
| --- | --- | --- | --- |
| A：经 Deneb 拉 20MB | 0/39、0/38 | 0/52、0/49 | 0 |
| B：不经 Deneb，scp 拉 20MB | 0/38、0/36 | 0/50、0/44 | 0 |
| C：暂停工作室 | 0/39、0/38 | 0/53、0/47 | 0 |

- 整个 7.5 分钟里，Google 284 次只失败 1 次（21:45:53），出现在最后一段安静期，离最近的操作已经过了一分多钟。国内网站 370 次全部成功。
- mihomo 的警告级日志流全程保持连接，一条警告都没有。

**判断**：这两段超时不是 Deneb 和 Clash TUN 冲突造成的，最可能是 Clash 节点自身的波动。依据有三条：

1. 六个可能冲突的方向逐条核对，没有任何一处是两边共用的。
2. 两个操作反复做都没有再引起超时。不经 Deneb 的同样大流量也没有。
3. Google 走的美西-Hy2 跑在 UDP 上，而那段时间家里宽带出境的 UDP 丢包很重；网卡出现之前也有过同样一段十几秒的超时（20:14:55–20:15:12）。

⚠️ 剩下的不确定：

- 复现是在用户态模式下做的，内核网卡模式没有再建一次。理由是这两种模式里，可能影响 Clash 的只有 Wi-Fi 上的流量，scp 对照已经覆盖了。如果要彻底坐实，需要再建一次网卡，那要用户同意并输入密码。
- 那两段时间 mihomo 的日志没有留存，所以"节点自身波动"是推断，不是从它的日志里看到的。

**引擎这边要怎么做**（正式实现照此执行）：

1. **发往公网的包绑物理网卡**：打洞用的 UDP、STUN、连中转站的 TLS 都绑物理网卡（macOS 用 IP_BOUND_IF，Windows 用 IP_UNICAST_IF，Linux 用 SO_BINDTODEVICE）。这样 Deneb 的流量不进代理软件的 TUN，两边不会共用任何套接字或连接表。不绑的后果见 §6.5：直连会被送到代理节点绕一圈。绑网卡后连不上中转站时，才退回走系统路由。
2. **地址和路由只占自己那一小块**：地址段避开 `100.64.0.0/10`（Tailscale）和 `198.18.0.0/15`（Clash、Surge），只装一条覆盖自己 `/16` 的路由，不碰默认路由。启动和换网时先做空跑检查（原型的 `-preflight`）：这一段只能被代理软件的大路由覆盖，不能有更具体的路由或网卡地址；不满足就换一段，或者退回用户态。
3. **DNS 只接管 `deneb.internal`**：用分域解析，服务地址放在自己的 `/16` 里，其余查询一概不碰，Clash 的 DNS 劫持照常工作。
4. **产品里不碰代理软件**：不写它的配置，也不调用它的控制接口。要判断本机有没有代理软件的 TUN，只读路由表：0/8 以外的 IPv4 被 1/8 到 128/1 这类大路由接管，网卡地址在 198.18 段。读到了就在"更多"里写一句"Deneb 只接管 10.86.x 和 .deneb.internal，代理软件的流量不经过 Deneb"，用户怀疑"装了 Deneb 以后翻墙变卡"时有据可查。
5. **网卡和路由尽量少变动**：只在加入第一个局域网时建网卡，退出最后一个局域网时拆；加入、暂停、退出局域网只改引擎里的表（§6.3、§6.8 实测这些操作不影响别的连接）。
6. **不需要为代理软件限速**：两轮 20MB 传输都没有影响 Clash，暂时不用给 Deneb 的大流量限速或降低优先级。
7. **排查办法写进测试规范**（这是测试时的做法，不是产品功能）：
   - 测共存时，同时只读接收代理软件的警告级日志（mihomo 的本地控制套接字只用 `GET /logs` 和 `GET /proxies`）；
   - 每个可疑操作都配一组不经 Deneb 的对照；
   - 监控期间不同时做别的大流量操作。

## 7. 没验证的、风险和下一步

**没有验证的：**

1. **Windows 和 Linux 上的内核网卡**：Windows 用 Wintun 加 NRPT，Linux 用 tun 加 systemd-resolved。macOS 已验证（§6.8）；另外两个要改测试机的网络配置，同样得先确认。
2. **两台都在 NAT 后面的跨网直连**：Mac 回到家里 Wi-Fi 后，和 Windows 测试机在同一个家庭网络，测到的是局域网直连；之前在手机热点上则打不了洞。两边在不同的普通家庭网络时还没测。
3. **真实的内核转发**：Linux 用内核网卡并开着 IP 转发时，出口那一关要拦住借道的包。规则有单元测试，但没在真实内核上测；可以在 colima 容器里做，不影响任何机器。
4. **多个中转站**：中转站按局域网分组、对端常驻在不同中转站的情况。
5. **手机**：只有一个 VPN 位置，以及 iOS 网络扩展的内存上限。
6. **控制面**：实时下发、地址分配和冲突检查、密钥轮换。
7. **过滤代码的安全审查**：IP 分片、IPv6 扩展头、ICMP 错误报文等边界情况。

**风险：**

- 隔离完全靠自己写的过滤代码。正式实现要有单元测试、模糊测试和攻击用例，原型的 §6.4 可以作为起点。
- 一个 `/16` 每个部署约 6.5 万台设备，做成公共服务后必须换方案（一个租户一个 `/16`，或者以 IPv6 为主）。
- 中转站的线路质量直接决定"经中转"的体验。本次 hk-spare 的中转延迟在 300–650ms 之间波动，这和调研 §5.7 的结论一致：中转站要离用户近、线路要好。
- 直连也会"连着但很差"：家里 Wi-Fi 上，hk-155 发回本机的 UDP 被丢了约 20%，同一时间普通 ping 一个不丢（§6.8）。原型和 Tailscale 一样，只看直连"有没有回应"，丢包这么多仍会留在直连上，TCP 因此卡住。正式实现要按丢包率和延迟决定走直连还是中转。

**下一步建议（按顺序）：**

1. 按 §4 定下技术方案：一个引擎、一台设备一个地址、四层隔离、绑物理网卡。DESIGN §12 第 9 条（"同时在几个局域网的前提"）可以改为"已验证"。
2. 在 Windows 测试机上验证内核网卡（Wintun 加 NRPT），做法照搬本机这一轮：空跑检查、全程监控、只在开始和结束各改一次。这也属于改网络配置，同样先确认。
3. 路径选择加上质量判断：直连丢包或延迟明显比中转差时，改走中转（§6.8 的 20% 丢包就是这种情况）。
4. 评估在 Tailscale 开源客户端底层上改造的工作量：magicsock、netstack、各平台路由和 DNS 管理分别能复用多少。
5. 产品侧：
   - "直接连上 / 经中转"换状态要防抖，建议持续 2 秒以上才换画面。
   - 暂停、恢复几乎是瞬间的，可以照 demo 做。
   - 手机只有一个 VPN 位置的问题，要尽早想产品上的出路。

- **S5** · Tailscale `net/netmon/state.go` 的 `HasCGNATInterface` 和 `isTailscaleInterface`：别的网卡有 100.64/10 的地址就算"有 CGNAT 网卡"；1.92 起的 macOS 应用会明确告诉它哪张是自己的网卡，所以 Deneb 的 utun 不会被误认成 Tailscale 自己的。`net/netmon/netmon_darwin.go` 的 `isInterestingInterface`：utun 开头的网卡及其路由变化不算网络变化。
- **S6** · Tailscale `util/linuxfw/nftables_runner.go` 的 `addDropCGNATRangeRule`：Linux 上丢弃不是从 Tailscale 网卡进来、来源地址在 100.64/10 的包。
