# 只用 Cloudflare，不再依赖任何服务器（11-17）

> 方案，主会话写，等用户看。用户 11-17 定了方向（§1），这里写怎么搬、用户会碰到什么、每月多少钱、要用户定的几件事（§9）。用户点头以前一样都不动。
> 本文不写真实 IP 和域名：两台香港机器照惯例叫 hk-155（控制服务器那台）、hk-spare（网页那台）；域名用部署文件里的名字：`WEB_HOST`（网页、官网、下载站）、`CONTROL_TUNNEL_HOST`（现在经 Cloudflare 进控制服务器的那个）、`RELAY_TUNNEL_HOST`（现在经 Cloudflare 进公共中转站的那个）。
> Cloudflare 的价格、限制、条款都是 11-17 照它的文档原文查的，页面写在 §11。

## 0. 一句话

控制服务器和公共中转站的程序原样放进 Cloudflare 的容器（Containers），数据库实时复制到 Cloudflare 的对象存储（R2）；官网、网页版、下载站放到 Workers 和 R2。域名都不变，0.1.9 起的设备不用操作。中转站缺的 STUN 换成 Cloudflare 免费的那个，为此出一版 0.1.10。照推荐的做法（三个地区的中转站）每月约 30 美元，只开一个中转站约 15 美元。

## 1. 用户定的（11-17）

- Deneb 服务美国和海外的用户，不服务中国大陆。
- 整个项目只部署在 Cloudflare 上，不依赖任何服务器，官网也一样。hk-155、hk-spare 上属于 Deneb 的东西都要停掉。
- 公共中转站就靠 Cloudflare。想要延迟更低，用户自己装中转站（"我的服务器"）。
- 下载放 Cloudflare 的对象存储（R2）或者 GitHub Releases。

## 2. 用户会碰到什么

- **已经在用的人**：每搬一步，设备最多断开几秒，然后自己连回来。网址、下载链接、登录都不变，不用重新登录。
- **0.1.9 起的设备**：什么都不用做。0.1.9 本来就会在直连不通时改走 `CONTROL_TUNNEL_HOST`，搬完以后它走的就是这条路。
- **0.1.8 及以前的设备**：只认 hk-155 的地址。搬控制服务器以前必须更新到 0.1.9 或以后，不然会一直"连不上 Deneb 服务器"。
  - macOS、Windows 的窗口里会提示更新。
  - Linux 的 `.deb` 不会自己更新，要自己装新版。
  - 搬之前在运营后台数一下还剩几台旧版本，列给用户（§9 第 6 件）。
- **自己装了中转站的人**：中转站每 6 小时左右自己查一次新版本，更新到认得新地址的版本就行，不用管。关了自动更新、或者装得很早的，要照新的一行命令重装一次。
- **走中转时的快慢**：
  - 美国、欧洲的用户：Cloudflare 的机房离得近，一般比现在绕到香港快。
  - 其他地区：走最近的一个公共中转站，比自己装的慢。想快就自己装一个。
  - 设备之间能直连的（大多数情况）不经过中转站，不受影响。
- **Cloudflare 出问题时**：设备之间已经直连的照常能用；但登录不了、改不了设置，走中转的连不上，直到 Cloudflare 恢复。现在两台服务器任何一台出问题也是这样，区别是以后全看 Cloudflare 一家（§8 第 1 条）。
- **撤回**：每一步都能退回上一步（§6）。hk-155、hk-spare 留到全部搬完再观察两周才停。

## 4. 每一样怎么搬

### 4.1 控制服务器

- **怎么跑**：现在的 Go 程序打成镜像，放进 Cloudflare Containers，用一个 Durable Object 管着，保证同一时间只有一份在跑。大小先用 lite（1/16 vCPU、256 MiB 内存、2 GB 硬盘）：现在它只用 15 MiB 内存、不到 1% 的 CPU。
- **怎么进来**：设备、网页版、自己的中转站都连 `CONTROL_TUNNEL_HOST`。一个 Worker 把请求转给容器。容器只收这一条路来的明文 HTTP，从 `CF-Connecting-IP` 拿设备的地址。这和现在的 `-tunnel-listen` 一样，程序几乎不用改。
- **数据库**：容器的硬盘不保留，重启或换机器就清空，Cloudflare 也不保证容器一直跑（会先发 SIGTERM 再停）。所以：
  - 用 Litestream 把 SQLite 每秒复制一次到 R2；
  - 容器每次启动，先从 R2 取回数据库再开门。4.8 MB 一两秒就取回了；
  - 正常停（收到 SIGTERM）不丢数据。容器突然死掉，最多丢最后一秒写的东西；
  - 同一时间只有一份在写：靠 Durable Object 保证，启动时再核对 Litestream 的代数，对不上就不开门、报警。
- **备份**：每天的备份改成写到 R2，照旧最近 7 天每天一份、往前 8 周每周一份，用 R2 的生命周期规则到期删除。升级前的整份拷贝也放 R2。签名用的私钥照旧不进备份。
- **日志**：照旧一天一个文件，每分钟把当天的文件传一份到 R2，30 天到期删除。网页运营后台照旧能看今天和昨天的。
- **配置和密钥**：发信、报警、种子账号、签名私钥放在 Cloudflare 的 Secrets 里，不进仓库，也不进镜像。
- **管理命令**：现在靠 `docker exec`，容器里做不到。日常的操作都在网页运营后台；还没搬上去的（比如批准测试设备登录）补到运营后台。
- **发信**：现在经 Resend 的 SMTP。容器能不能往外连 SMTP 端口要实测，不行就改用 Resend 的 HTTPS 接口。
- **从外面检查自己装的中转站**：
  - TCP 加 TLS 握手，容器里照做；
  - UDP 的 STUN 检查要实测容器能不能往外发 UDP；发不了就只查 TCP，卡片上照实说"UDP 没法从外面查"；
  - 原来"运营方另一台机器"的第二个检查点，改成 Worker 的定时任务，只能查 TCP。

### 4.2 公共中转站

- **怎么跑**：现在的中转站程序（Tailscale 的 DERP，加准入和记流量）原样放进 Cloudflare Containers，只走 WebSocket：`wss://<中转站域名>/derp`。0.1.9 经隧道时就是这样连的，域名照旧用 `RELAY_TUNNEL_HOST`，所以 0.1.9 的设备连得上。
- **大小**：basic（1/4 vCPU、1 GiB）。11-17 取样时它在 hk-155 上用了将近 8% 的一个核，lite 的 1/16 核可能不够。能转多快要实测。
- **准入和记流量照旧**：中转站照旧问控制服务器，只是改成经 `CONTROL_TUNNEL_HOST`。
- **收不了 UDP**：容器只能经 Worker 收 HTTP 和 WebSocket，所以：
  - 中转照旧走 TCP，和现在一样，没有差别；
  - 中转站没法再当 STUN 服务器（帮设备查自己的外网地址，打洞要用）。改用 Cloudflare 的 `stun.cloudflare.com:3478`，Cloudflare 写明免费、不限量。
- **地区**：先开美西、美东、欧洲三个，以后看用量再加亚洲。容器是在第一次请求的位置附近挑机房的，能不能放到想要的地区要实测。
- **0.1.9 有两处不够，要出 0.1.10**：
  - 0.1.9 只从中转站拿 STUN 的地址。中转站搬走以后，没装自己中转站的设备就查不到外网地址，打洞成功率会下降，走中转的会变多。0.1.10 改成控制服务器在网络图里单独给 STUN 的地址。
  - 0.1.9 每次都先试中转站的直连地址，连不上才走 WebSocket。只有 WebSocket 一条路的中转站，0.1.9 能不能好好用要实测。0.1.10 让中转站可以只有 WebSocket。
- **为什么不用 Durable Objects 自己写一个**：一个对象每秒最多约 1000 次请求，一个包算一次，一个对象只能转十来 Mbps；还要用 JS 重写 DERP。容器能原样跑现在的程序。
- **为什么不用 Cloudflare 的 TURN**：它走 UDP、全球就近，最合 WireGuard；每月 1000 GB 以内免费，之后每 GB 0.05 美元。但引擎要新做 TURN，工作量大，留到以后再看。

### 4.3 官网和网页版

- 官网和网页版的页面放进 Workers 的静态资源。网页版原来由 deneb-web 转给控制服务器的那些请求，改由 Worker 转给控制服务器的容器。nginx、deneb-web 都不要了。
- 网址照旧是 `WEB_HOST`，证书换成 Cloudflare 的。
- 浏览器的地址由 Worker 带给控制服务器，附一个只有这两边知道的密钥，控制服务器见到密钥才信这个地址（现在是 `-trust-proxy` 只信 deneb-web）。
- 访问日志照旧不记，因为路径里有邀请码。Worker 只记错误，Workers Logs 留 7 天。

### 4.4 下载

- 安装包、更新包、更新清单放在 R2，经 `WEB_HOST/download/` 由 Worker 读出来。R2 往外传不收费。
- 已经装好的应用按编在里面的地址查更新。地址不变，所以照样能更新，也能更新到 0.1.9、0.1.10。
- GitHub Releases 同时放一份，下载页可以指过去。
- 自己装中转站的那一行命令 `curl -fsSL https://<WEB_HOST>/relay | sh` 照旧能用，脚本和中转站的发行版也放 R2。
- `deploy/web/publish-downloads.sh` 改成传到 R2。

### 4.5 看门狗和报警

- 一个 Worker 的定时任务每分钟查一次控制服务器和每个公共中转站：控制服务器的健康检查，中转站的 WebSocket 握手。有问题照原来的规则报警，现在只记日志，以后接群机器人。

## 5. 0.1.10 要改什么

- **引擎**：
  - 网络图里多一项 STUN 服务器的地址（域名加端口），和中转站的 STUN 一起用；
  - 中转站可以只有 WebSocket 一条路，不先试直连；
  - 连控制服务器的入口里，`CONTROL_TUNNEL_HOST` 排第一。hk-155、hk-spare 停了以后，从入口清单里去掉。
- **自己装的中转站**：
  - 认得控制服务器的新地址：原来记的是 hk-155 的地址，更新后自己换成 `CONTROL_TUNNEL_HOST`；
  - 照旧自己更新。
- **控制服务器**：
  - 给 0.1.10 起的设备列新的公共中转站，给旧版本照旧列 hk-155 上那个，直到 hk-155 停掉；
  - 网络图里给 STUN 的地址。

## 6. 搬的顺序

每一步上线前都要用户点头（AGENTS.md §3），每一步都写了怎么退回。

0. **先发 0.1.9**（已经在做）：设备认得经 `CONTROL_TUNNEL_HOST` 去连控制服务器。
1. **用户在 Cloudflare 后台开 Workers 付费套餐**（每月 5 美元），给部署用的 API 令牌。
   - 付款和令牌都由用户自己操作；令牌放钥匙串或不进仓库的文件，不进聊天。
2. **官网、下载站、网页版搬到 Worker 加 R2**。
   - 网页版这时先经现在的隧道，连 hk-155 上的控制服务器。
   - 退回：把 `WEB_HOST` 改回指向 hk-spare。
3. **发 0.1.10**，等大多数设备更新。在运营后台看各个版本各有几台。
4. **公共中转站搬进容器**：控制服务器给 0.1.10 起的设备列新的，旧版本照旧列 hk-155 上那个。
   - hk-155 停掉以前，0.1.9 的设备也改列新的。这要先实测 0.1.9 能用只有 WebSocket 的中转站（§8 第 6 条）。0.1.8 及以前的用不了 WebSocket，不过那时它们也连不上控制服务器了。
   - 退回：不再列新的。
5. **控制服务器搬进容器**：
   - 停掉 hk-155 上的控制服务器，数据库传到 R2，容器启动取回，`CONTROL_TUNNEL_HOST` 从隧道改到 Worker；
   - 估计停几分钟。这期间设备之间照常通，只是登录不了、改不了东西；
   - 退回：数据库从 R2 拿回 hk-155，`CONTROL_TUNNEL_HOST` 改回隧道。
6. **看门狗搬到 Worker**。
7. **观察两周**，没问题再停 hk-155、hk-spare 上属于 Deneb 的容器。

## 8. 风险

1. **全靠 Cloudflare 一家**：账号被停或者 Cloudflare 大面积出问题，整个服务一起停，只有已经直连的设备照常能用。缓解：数据库每天另存一份到 Cloudflare 以外（§9 第 5 件）。
2. **条款**：Cloudflare 写明，传视频和大文件要用开发者平台这类付费服务，免费的 CDN 不行。Workers 和容器就是开发者平台。反过来看，现在用免费隧道转中转流量才是不合条款的用法，搬完就没有这个问题了。
3. **容器会重启**：Cloudflare 不保证容器一直跑，主机重启时会换一台重开，冷启动 1 到 3 秒，加上取回数据库的时间。设备会断开几秒再连上，设备之间的直连不受影响。
4. **控制服务器的身份**：以前设备核对 hk-155 证书的指纹；以后只认 Cloudflare 的正式证书。Cloudflare 看得到设备和控制服务器之间的全部内容。现在走 Cloudflare 这条路时已经是这样，以后每台设备都这样。
5. **隐私说明要跟着改**：数据放在 Cloudflare 上，不再是香港；Cloudflare 是托管方；备份和日志放在 R2；不再有"运营方的另一台服务器"。和搬的那一步一起改。
6. **要实测才知道的**：
   - 容器能不能往外发 UDP、连 SMTP 端口；
   - 只有 WebSocket 的中转站，0.1.9 能不能好好用；
   - 设备连控制服务器的长连接，在 Worker 转容器这条路上能不能一直挂着（Cloudflare 一般 100 秒没有数据就断，控制服务器的保活要比这个短）；
   - 中转站容器能不能放到想要的地区、一个 basic 能转多快。

   这些都在第 2 步以前，用一个测试账号在 Cloudflare 上试，试完写进本文。

## 9. 要用户定的

1. **控制服务器怎么放**：
   - 推荐：原样放进容器，数据库复制到 R2；
   - 不推荐：用 Workers 重写，等于重写整个服务器。
2. **公共中转站怎么放，开几个地区**：
   - 推荐：容器里跑现在的程序，先开美西、美东、欧洲三个；
   - 不推荐：用 Durable Objects 重写，转不快；
   - 以后再看：Cloudflare 的 TURN。
3. **下载放哪**：
   - 推荐：R2 为主，GitHub Releases 放一份；
   - 也可以：只放 GitHub Releases。不过已经装好的应用查更新的地址编在应用里，`WEB_HOST/download/` 还得留着，由 Worker 转到 GitHub。
4. **先发哪一版**：
   - 推荐：0.1.9 照原计划先发（Windows 真机测完就发），中转站要的改动放进 0.1.10。
5. **数据库要不要每天另存一份到 Cloudflare 以外**：
   - 推荐：要。加密以后存到 GitHub 的私有仓库，防 Cloudflare 账号出事。
6. **搬控制服务器时还没更新的旧设备怎么办**：
   - 推荐：等到只剩个位数再搬。剩下的设备会一直连不上，直到装了新版。

## 11. 依据（Cloudflare 文档，11-17 查的原文）

- 容器：
  - 价格 `developers.cloudflare.com/containers/pricing/`：要付费套餐；内存每 GiB 秒 0.0000025 美元，每月含 25 GiB 小时；CPU 按实际用的算，每 vCPU 秒 0.00002 美元，每月含 375 vCPU 分钟；硬盘每 GB 秒 0.00000007 美元，每月含 200 GB 小时；往外的流量北美、欧洲每 GB 0.025 美元，每月含 1 TB。
  - 规格 `containers/platform-details/limits/`：lite 1/16 vCPU、256 MiB、2 GB；basic 1/4 vCPU、1 GiB、4 GB。
  - 常见问题 `containers/faq/`：硬盘默认不保留；主机不定期重启，停之前先发 SIGTERM，可能换一台重开；冷启动常见 1 到 3 秒。
- Durable Objects（`durable-objects/platform/pricing/`、`limits/`）：
  - 免费和付费套餐都有；
  - 收到的 WebSocket 消息 20 条算 1 次请求，发出去的不算；
  - 一个对象每秒约 1000 次请求的软上限。
