# M7 · 控制服务器的备份、恢复、监控和备机

> 控制线，2026-11-10。§1、§2 做好了，本机测过，没上线，上线要用户点头。§3 到 §5 是方案，都没做。没碰 hk-155、hk-spare 上跑着的东西，只读看过 hk-155 上备份目录的文件名和大小。

## 1. 每天的备份（做好了，本机测过，没上线）

**原来就有的**：服务器每小时看一次，当天（按 UTC）还没有备份，就用 `VACUUM INTO` 写一份 `<数据目录>/backup/deneb-YYYYMMDD.db`，保留 7 份。hk-155 上一直在跑，11-07、11-08、11-09 各有一份，150 到 210 KB。

**这次改的**：

- **先写临时文件**：写完后检查（`quick_check`）通过、改成 0600、落盘，才换成正式的名字。崩溃留下的半份，下一次会被删掉，不会冒充当天的备份。
- **备份里不放签名密钥**：删的时候开了 `secure_delete`，日志只放在内存里，文件里一个字节都不留。
  - 恢复以后服务器自己生成新的密钥，设备拿到 401 会自己重新认证。11-09 换密钥时验证过，五台设备 1 秒内都回来了。
  - 网页会话不受影响：库里存的是会话的哈希，不靠签名密钥。
  - 这样备份就算泄露，也没法拿来冒充设备。
- **权限**：备份文件 0600，备份目录 0700。
- **保留**：最近 7 天每天一份，再往前每周留最新的一份，留 8 周。数据库现在 200 KB 上下，两个月 15 份，不到 4 MB。
- **看备份**：新管理命令 `deneb-control backups`，列出每一份的名字、大小和写入时间。
- **测试**：`TestBackup` 覆盖：
  - 权限对；
  - 签名密钥连字节都不在文件里，线上库里的还在；
  - 同一天不重复写；
  - 崩溃留下的半份不碍事；
  - 拿备份恢复后，服务器有了新密钥，旧令牌不认，设备重新认证后一切照旧。

  `TestBackupsKept` 覆盖保留规则。

**还缺的，要用户定**：

- **备份和服务器在同一块盘上**：机器没了，备份也就没了，要拷到别处（§5）。
- **TLS 私钥不在每天的备份里**：它丢了，所有设备认的指纹就都对不上了，要单独存一份在别处（§5）。

## 2. 恢复演练，和真要恢复时怎么做

**演练脚本**：`deploy/control/restore-drill.sh`。

- **在本机**：

  ```
  deploy/control/restore-drill.sh <备份文件> [种子文件]
  ```

  脚本把备份拷进一个只有自己能读的临时目录，用工作区的服务器代码打开（会迁到最新版本），做完检查就删掉临时目录。
- **在服务器上**，数据不离开服务器：

  ```
  HOST=hk-155 deploy/control/restore-drill.sh [deneb-YYYYMMDD.db]
  ```

  - 脚本在本机编好 linux/amd64 的检查程序，传到服务器 `/tmp` 下一个 0700 的临时目录。
  - 从 `backup/` 拿最新的一份（或者指定的那份），用服务器自己的种子文件检查。
  - 做完连目录一起删掉。服务器上会有一分钟多出这些文件，所以要先问。
- **检查什么**（`TestRestoreDrill`）：
  - 完整性（`integrity_check`）；
  - 签名密钥在不在里面：只说在不在，不打印；
  - 能起来，并迁到最新版本；
  - 每台设备都有主人；
  - 在用的设备地址不重复、都在地址段里，网络图建得出来，对端都是在用的设备；
  - 每个局域网的拥有者都在里面。

  打印的只有个数和版本号。
- **本机测过**：
  - 本地做了一份备份，演练通过；
  - `HOST=.` 在本机模拟服务器那一半：目录照 hk-155 的样子摆，放两份备份，取的是最新的一份，通过；
  - 检查程序编 linux/amd64 能编过。

**真要恢复时**（写下来了，没做过）：

1. 先在服务器上，对要用的那份备份跑一遍演练。
2. 停服务：`docker stop -t 10 deneb-control`。
3. 把现在的数据目录整个另存一份：`cp -a data data.before-restore-<时间>`。
4. 删掉 `data/deneb.db`、`deneb.db-wal`、`deneb.db-shm`，把备份拷成 `data/deneb.db`，再 `chown 65534:65534`、`chmod 600`。`tls/` 和 `seed.json` 不动。
5. 起服务：`docker start deneb-control`。服务器会生成新的签名密钥，设备很快自己重新认证。
6. 核对：`/healthz`、`deneb-control relays`，前后给五台设备各拍一次快照比对。

**会丢什么**：备份之后的改动，最多一天的。这段时间里新登录的设备要重新登录；新建的局域网、邀请、分享要重做；这之后才登录的网页也要重新登录。

恢复到另一台机器（备机）见 §5。

## 3. 监控和提醒（方案，没做）

现在有的：

- 容器健康检查，挂了 docker 会自己重启；
- 日志；
- `deneb-control relays`、`backups`、`sessions` 几条命令；
- 中转站每分钟向控制服务器同步一次，3 分钟没同步就算离线。

可是出了事，没有人会被叫醒。

### 看什么

| 看什么 | 怎么知道 | 什么时候提醒 |
| --- | --- | --- |
| 控制服务器不通 | 另一台机器每分钟请求一次 `https://103.42.31.155:47443/healthz` | 连续 2 次失败；恢复了也说一声 |
| 控制服务器的容器不健康、反复重启、因内存不够被杀 | 本机看 `docker inspect` 里的健康状态、重启次数、`OOMKilled` | 一出现就提醒 |
| 公共中转站离线 | 控制服务器自己知道 | 离线超过 3 分钟。"我的服务器"离线，主人在界面上看得到，不提醒运营 |
| 公共中转站满了 | 控制服务器自己知道 | 满了超过 10 分钟 |
| hk-spare 上的旧中转站 `hk` | 另一台机器探它的 HTTPS 和 STUN | 连续 2 次失败 |
| 备份 | 最新一份的时间；日志里 `backup:` 开头的错误 | 超过 26 小时没有新的，或者报错 |
| 磁盘、内存 | `df`；容器内存，上限是 256 MB | 磁盘剩不到 15%；内存超过 200 MB |
| 在线设备突然变少 | 控制服务器的在线数 | 5 分钟内掉了一半以上，多半是服务器或网络出了事 |
| 出错多、被大量请求 | 日志里 5xx、429 的个数 | 先观察一周再定阈值 |
| 证书 | 自签证书 397 天有效，到期前 30 天服务器用同一把私钥自己续，指纹不变 | 只在续失败时提醒 |

### 提醒发到哪（要用户定）

选一个就够，都只要给一个链接或令牌：

- 企业微信、飞书或钉钉的群机器人：发到一个群，手机上就有通知；
- Telegram 机器人；
- Bark（iPhone 推送）；
- 邮件：要一个能发信的邮箱账号。以后发登录验证码也要它（[control-security.md](control-security.md) 要定的第 1 条），可以合用。

推荐先用一个群机器人；以后做了发邮件，再加上邮件。

### 怎么做（定了再做）

- **控制服务器自己知道的事，它直接发**：加一个 `-alert-webhook` 参数。中转站离线、恢复、满了，备份失败，磁盘不够，这些都直接发出去；同一件事 30 分钟内只发一次。
- **控制服务器挂了它自己发不了**，所以在另一台机器上跑一个很小的看门狗：一个容器，不占端口，只往外发请求。
  - 每分钟探一次对方的 `/healthz`、两个中转站、`hk` 旧中转站，失败了发到同一个地方。
  - hk-155 和 hk-spare 互相看。
- 都只往外发请求，不改两台机器的网络和防火墙，不碰别的服务。
- 统计（在线设备、操作数、出错数）先从日志里数。要画图时再加 `/metrics`，只开在管理套接字上，不对外。

## 4. 地址池够多少人用

- **怎么分**：每个部署第一次启动时，在 10.0.0.0/8 里随机挑一个 /16，避开 10.0–10.47、10.96–10.111、10.128 往上，和几个整数、吉利数。hk-155 是 10.48.0.0/16。一台设备一个 IPv4，外加一个由它算出来的 IPv6，在所有局域网里都一样。
- **一共多少**：第三段 1 到 255、第四段 1 到 254，一共 64,770 个。
  - 第三段为 0 的（.0.0 到 .0.255）留给服务器，DNS 在 .0.53；
  - .x.0 和 .x.255 看着像网络地址和广播地址，不用。
- **地址跟着设备走，不看在不在线**：登出了、登录过期了，设备都留着地址，这样同一个人再登录，还是原来的地址。只有别人在同一台机器上登录，旧设备才被删掉，它的地址冷却 30 天后再给别人。
- **够多少人**：按一个人 3 台设备算，大约 2 万人。公测几百到几千人，绰绰有余。
- **会慢慢变少**：试一下就走的人，他们的设备一直占着地址。建议用到一半（3 万多个）时加一条清理：登出或过期超过 180 天的设备删掉，地址冷却后再用。
- **真要超过一个 /16**：现在网络图里只有一个地址段，引擎按它设路由。
  - 扩容就是给部署再加一个 /16，要改协议（网络图里的地址段变成多个），引擎也要跟着改。
  - 不能直接换成更大的段，那样所有人的地址都要变。
  - 建议用到 80% 时再做，离现在还很远。
- **地址用完之前，先撞上的是速度**：服务器每次改动都要把整个世界从库里重读一遍，设备一多，每次改动都会变慢。公测前要压测一次，看几千台设备时一次改动要多久。

## 5. 控制服务器要不要备机（方案，没做）

### 现在挂了会怎样

- 控制服务器在 hk-155 上，一个容器，用 SQLite。公共的香港中转站也在 hk-155 上。
- hk-155 挂了：
  - 已经连着的设备之间照常通：数据直接走或经中转站，网络图就在设备上；
  - 公共的香港中转站跟着挂了，设备改走 hk-spare 上的旧中转站 `hk`，还能中转；
  - "我的服务器"中转站问不到控制服务器，就不放新连接进来；公共中转站问不到时放行；
  - 不能新登录、不能做任何改动；换了网络的设备，找不到彼此的新地址。
- 设备连控制服务器，用的是 IP 地址 103.42.31.155，认的是 TLS 私钥的指纹。所以要换一台机器接替，要么用同一个 IP，要么所有设备都改地址。现在做不到不打扰用户地换机器。

### 建议，按先后

1. **控制服务器的地址换成域名**，比如 `control.<域名>`。
   - 以后备机接替，只要改 DNS；正式证书（[control-security.md](control-security.md) 要定的第 8 条）也要域名。
   - 要用户买或者给一个域名。
   - 设备那边怎么改用域名，引擎线来看。指纹不变，设备不用重新认证书。
2. **备份和 TLS 私钥各存一份在别的地方**：
   - 每天的备份拷到 hk-spare：在 hk-spare 上加一条定时任务，从 hk-155 拉过来，存成 0600，只有 root 能读。备份里已经没有签名密钥了。
   - TLS 私钥（`data/tls/`）只存一次，交给用户自己保管，比如加密以后放进密码管理器，不放在 hk-spare 上。它丢了，所有设备都要重新认；它泄露了，别人就能冒充服务器。
3. **冷备机**：hk-155 挂了，就在 hk-spare 上用最新的备份和 TLS 私钥起一个控制服务器，再改 DNS。
   - 目标：30 分钟内恢复，最多丢一天的改动。
   - 写一个 `failover-hkspare.sh`，演练一次，要用户点头。
4. **以后要少丢一点**：SQLite 持续复制（Litestream 这类工具，把写入日志不停地传到对象存储或另一台机器），最多只丢几秒。要下载新工具，得用户同意；公测人多了再做。

不建议现在做双活或自动切换：SQLite 只能有一边写，两边都以为自己是主的话，数据会分叉；也没有云上的负载均衡，服务器的网络又不能动。
