## 1. 每天的备份（11-10 23:08 上线；新格式的第一份在 11-11 UTC 0 点以后写）

**原来就有的**：服务器每小时看一次，当天（按 UTC）还没有备份，就用 `VACUUM INTO` 写一份 `<数据目录>/backup/deneb-YYYYMMDD.db`，保留 7 份。hk-155 上一直在跑，11-07、11-08、11-09 各有一份，150 到 210 KB。

**这次改的**：

- **先写临时文件**：写完后检查（`quick_check`）通过、改成 0600、落盘，才换成正式的名字。崩溃留下的半份，下一次会被删掉，不会冒充当天的备份。
- **备份里不放签名密钥**：删的时候开了 `secure_delete`，日志只放在内存里，文件里一个字节都不留。
  - 恢复以后服务器自己生成新的密钥，设备拿到 401 会自己重新认证。11-09 换密钥时验证过，五台设备 1 秒内都回来了。
  - 网页会话不受影响：库里存的是会话的哈希，不靠签名密钥。
  - 这样备份就算泄露，也没法拿来冒充设备。
- **权限**：备份文件 0600，备份目录 0700。M7 以前写的备份是 0644；11-10 起，每天写备份时也把留着的旧备份收紧到 0600。这一条还没上线，下次部署后生效。
- **保留**：最近 7 天每天一份，再往前每周留最新的一份，留 8 周。数据库现在 200 KB 上下，两个月 15 份，不到 4 MB。
- **看备份**：新管理命令 `deneb-control backups`，列出每一份的名字、大小和写入时间。
- **测试**：`TestBackup` 覆盖：
  - 权限对；
  - 签名密钥连字节都不在文件里，线上库里的还在；
  - 同一天不重复写；
  - 崩溃留下的半份不碍事；
  - 拿备份恢复后，服务器有了新密钥，旧令牌不认，设备重新认证后一切照旧。

  `TestBackupsKept` 覆盖保留规则。

**还缺的，要用户定**：

- **备份和服务器在同一块盘上**：机器没了，备份也就没了，要拷到别处（§5）。
- **TLS 私钥不在每天的备份里**：它丢了，所有设备认的指纹就都对不上了，要单独存一份在别处（§5）。
- **hk-155 上的旧备份**：
  - `deneb-20261110.db` 是旧格式写的，带着现在这把签名密钥（11-09 21:18 换过），文件是 0644，放在 0700 的目录里。
  - 11-07 到 11-09 那几份带的是换掉以前的旧密钥，已经没用了。
  - 按保留规则，11-10 那份要到 11-18（UTC）写当天的备份时才会被删：那时同一周里有更新的一份出了"最近 7 天"，由它留作这一周的那份。
  - 在那以前，别把它拷出这台机器。要更早处理，可以在服务器上把它改成 0600 或者删掉，这要先问用户。

## 2. 恢复演练，和真要恢复时怎么做

**演练脚本**：`deploy/control/restore-drill.sh`。

- **在本机**：

  ```
  deploy/control/restore-drill.sh <备份文件> [种子文件]
  ```

  脚本把备份拷进一个只有自己能读的临时目录，用工作区的服务器代码打开（会迁到最新版本），做完检查就删掉临时目录。
- **在服务器上**，数据不离开服务器：

  ```
  HOST=hk-155 deploy/control/restore-drill.sh [deneb-YYYYMMDD.db]
  ```

  - 脚本在本机编好 linux/amd64 的检查程序，传到服务器 `/tmp` 下一个 0700 的临时目录。
  - 从 `backup/` 拿最新的一份（或者指定的那份），用服务器自己的种子文件检查。
  - 做完连目录一起删掉；中途出错也删，复制那一步就失败的话由本机这头去删。服务器上会有一分钟多出这些文件，所以要先问。
- **检查什么**（`TestRestoreDrill`）：
  - 完整性（`integrity_check`）；
  - 签名密钥在不在里面：只说在不在，不打印；
  - 能起来，并迁到最新版本；
  - 每台设备都有主人；
  - 在用的设备地址不重复、都在地址段里，网络图建得出来，对端都是在用的设备；
  - 每个局域网的拥有者都在里面。

  打印的只有个数和版本号。
- **本机测过**：
  - 本地做了一份备份，演练通过；
  - `HOST=.` 在本机模拟服务器那一半：目录照 hk-155 的样子摆，放两份备份，取的是最新的一份，通过；
  - 检查程序编 linux/amd64 能编过。
- **11-10 线上第一次跑出的毛病，已改**：
  - 不指定备份名时，空的备份名经 ssh 拼成一行命令就没了，远端只收到 3 个参数，在 `set -u` 下报错退出。清理还没设好，临时目录留在了服务器上（主会话已删）。
  - 改法：
    - 远端的参数每个都加单引号再拼，空的也是一个参数；
    - 远端脚本拿到临时目录后第一件事就设清理；
    - 本机这头也会去删，复制那步失败时临时目录也不会留下。
  - `HOST=.` 现在和 ssh 一样，先把命令拼成一行，再交给 shell，所以本机模拟走的是同一条路。原来本机模拟没走这条路，所以没测出来。
  - 重测了四种情况：不指定备份名（取最新的）、指定、给了路径（拒绝）、没有备份（报错退出）。另外故意让复制那步失败，看临时目录还删不删。四种都和预期一样，临时目录一个都没留下。

**真要恢复时**（写下来了，没做过）：

1. 先在服务器上，对要用的那份备份跑一遍演练。
2. 停服务：`docker stop -t 10 deneb-control`。
3. 把现在的数据目录整个另存一份：`cp -a data data.before-restore-<时间>`。恢复确认无误后删掉它：里面的日志和每天的备份不会自己过期（PRIVACY.md 第 7 节）。
4. 删掉 `data/deneb.db`、`deneb.db-wal`、`deneb.db-shm`，把备份拷成 `data/deneb.db`，再 `chown 65534:65534`、`chmod 600`。`tls/` 和 `seed.json` 不动。
5. 起服务：`docker start deneb-control`。服务器会生成新的签名密钥，设备很快自己重新认证。
6. 核对：`/healthz`、`deneb-control relays`，前后给五台设备各拍一次快照比对。

**会丢什么**：备份之后的改动，最多一天的。这段时间里新登录的设备要重新登录；新建的局域网、邀请、分享要重做；这之后才登录的网页也要重新登录。

恢复到另一台机器（备机）见 §5。

## 4. 地址池够多少人用，和压测

- **怎么分**：每个部署第一次启动时，在 10.0.0.0/8 里随机挑一个 /16，避开 10.0–10.47、10.96–10.111、10.128 往上，和几个整数、吉利数。hk-155 是 10.48.0.0/16。一台设备一个 IPv4，外加一个由它算出来的 IPv6，在所有局域网里都一样。
- **一共多少**：第三段 1 到 255、第四段 1 到 254，一共 64,770 个。
  - 第三段为 0 的（.0.0 到 .0.255）留给服务器，DNS 在 .0.53；
  - .x.0 和 .x.255 看着像网络地址和广播地址，不用。
- **地址跟着设备走，不看在不在线**：登出了、登录过期了，设备都留着地址，这样同一个人再登录，还是原来的地址。只有别人在同一台机器上登录，旧设备才被删掉，它的地址冷却 30 天后再给别人。
- **够多少人**：按一个人 3 台设备算，大约 2 万人。公测几百到几千人，绰绰有余。
- **会慢慢变少**：试一下就走的人，他们的设备一直占着地址。建议用到一半（3 万多个）时加一条清理：登出或过期超过 180 天的设备删掉，地址冷却后再用。
- **真要超过一个 /16**：现在网络图里只有一个地址段，引擎按它设路由。
  - 扩容就是给部署再加一个 /16，要改协议（网络图里的地址段变成多个），引擎也要跟着改。
  - 不能直接换成更大的段，那样所有人的地址都要变。
  - 建议用到 80% 时再做，离现在还很远。
- **地址用完之前，先撞上的是速度和内存**，见下面的压测。

### 压测（11-11，本机）

**怎么压**（`control/load_test.go`，`DENEB_LOAD=3000 go test ./control -run TestLoad -v`）：

- **造世界**：直接写进数据库，3 台设备一个人。每人有一个 3 个人、9 台设备的小局域网，每台设备看得到大约 14 台；另有一个 100 个人、300 台设备的"公司"局域网，`DENEB_LOAD_BIG=0` 时不建。
- **服务器**：用工作区的代码编出 deneb-control，单独一个进程，内存只算它自己的。和线上一样：
  - HTTPS 加 HTTP/2；
  - 一个 CPU（`GOMAXPROCS=1`，对应 `--cpus 1`）；
  - 堆上限 204 MB（256 MB 容器的八成）。
- **设备**：每台都用自己的机器密钥换令牌，在自己的连接上开推送流，三分之一带视图（桌面端就是这样）。所有流一齐开，模拟服务器重启后大家同时重连；被拒的稍等再连，引擎也是这样。
- **改动**：改局域网名字、开服务，计时到所有该收到的流都收到新版本为止。
- 数字是在这台 Mac 上量的。hk-155 的 CPU 慢一些，大概要乘 1.5 到 2。

**找到并改了的**：

1. **设备上线、下线，每台都算一次改动（最要紧）**：
   - 每次改动都要把所有推送流的网络图和视图重算一遍，转成 JSON 算哈希；一次改动，九成八的时间花在这上面。服务器一重启，N 台设备同时重连，就是 N 次改动、每次重算 N 份，耗时随 N 的平方涨。
   - 量过：300 台时一次改动 0.54 秒，重连要排两分多钟，这段时间里别的操作全在排队；3000 台时一次改动 1.05 秒，估计要排近一个小时。
   - 改法：上线、下线攒起来，最多每秒合并成一次改动，离线时写最后在线时间也一起写（`control/deviceapi.go`）。对端看到"在线 / 离线"最多晚一秒，别的都不变。
   - 改完：3000 台全部重连并收齐，5 到 11 秒。
   - 测试 `TestPresenceCoalesces`：5 台一起上线是一个版本，一起下线又是一个，最后在线时间都写了。
2. **内存会超过容器的上限**：
   - Go 默认等堆涨到上次活着的两倍才回收。几千条流时每次改动都产生大量垃圾，堆可能涨过容器的 256 MB，内核会直接杀掉服务器。
   - 改法：启动时读容器的内存上限，把 Go 堆的软上限设成它的八成；`GOMEMLIMIT` 设了就听它的（`cmd/deneb-control`）。
3. **每次改动的垃圾**：
   - 对端列表一次按大小分配，不再一个个往后加；
   - 算哈希时把帧编进复用的缓冲，没变的帧不再各留一份。
   - 3000 台时每次改动分配的内存从 193 MB 降到 133 MB，少了三成。

**改完的结果**：

| 在线设备 | 有没有 300 台的大局域网 | CPU | 堆上限 | 全部重连收齐 | 服务器内存（峰值 / 结束） | 一次改动 |
| --- | --- | --- | --- | --- | --- | --- |
| 999 | 有 | 1 | 204 MB | 4.7 秒 | 228 / 218 MB | 小局域网 0.5 秒；大局域网 0.6 到 1.4 秒 |
| 3000 | 没有 | 1 | 204 MB | 7.4 秒 | 283 / 287 MB，超过 256 | 1.0 秒 |
| 3000 | 有 | 1 | 204 MB | 11 秒 | 371 / 387 MB，超过 256 | 2.1 到 2.6 秒，回收内存时卡 |
| 3000 | 有 | 2 | 800 MB | 4.8 秒 | 572 / 600 MB | 0.5 到 0.7 秒 |

**结论**：

- **现在的容器能撑多少**：1 个 CPU、256 MB，大约 1000 到 1500 台同时在线。
  - 一台在线设备要占 80 KB 左右，主要是那条 HTTPS、HTTP/2 连接；
  - 再多就会超过 256 MB，有被杀掉的风险。
- **到 1500 台以上**：容器给 2 个 CPU、1 GB（部署脚本里的 `--cpus`、`--memory`）。hk-155 有 8 核、7.8 GB。要用户定。
- **还剩的**：
  - 每次改动仍然要把所有流重算一遍，代价是流的条数乘上每条的对端数。几百台设备的大局域网最费。
  - 以后可以只重算受影响的流，把每个对端编好的 JSON 在一次推送里共用（要改 proto），只重读变了的表。
  - 每条连接的内存也值得再查：TLS 和 HTTP/2 的缓冲。
  - 公测人数到上千以前都不急。

## 5. 控制服务器要不要备机（方案，没做）

### 现在挂了会怎样

- 控制服务器在 hk-155 上，一个容器，用 SQLite。公共的香港中转站也在 hk-155 上。
- hk-155 挂了：
  - 已经连着的设备之间照常通：数据直接走或经中转站，网络图就在设备上；
  - 公共的香港中转站跟着挂了，设备改走 hk-spare 上的旧中转站 `hk`，还能中转；
  - "我的服务器"中转站问不到控制服务器，就不放新连接进来；公共中转站问不到时放行；
  - 不能新登录、不能做任何改动；换了网络的设备，找不到彼此的新地址。
- 设备连控制服务器，用的是 IP 地址 103.42.31.155，认的是 TLS 私钥的指纹。所以要换一台机器接替，要么用同一个 IP，要么所有设备都改地址。现在做不到不打扰用户地换机器。

### 建议，按先后

1. **控制服务器的地址换成域名**，比如 `control.<域名>`。
   - 以后备机接替，只要改 DNS；正式证书（[control-security.md](control-security.md) 要定的第 8 条）也要域名。
   - 要用户买或者给一个域名。
   - 设备那边怎么改用域名，引擎线来看。指纹不变，设备不用重新认证书。
2. **备份和 TLS 私钥各存一份在别的地方**：
   - 每天的备份拷到 hk-spare：在 hk-spare 上加一条定时任务，从 hk-155 拉过来，存成 0600，只有 root 能读。备份里已经没有签名密钥了。
   - TLS 私钥（`data/tls/`）只存一次，交给用户自己保管，比如加密以后放进密码管理器，不放在 hk-spare 上。它丢了，所有设备都要重新认；它泄露了，别人就能冒充服务器。
3. **冷备机**：hk-155 挂了，就在 hk-spare 上用最新的备份和 TLS 私钥起一个控制服务器，再改 DNS。
   - 目标：30 分钟内恢复，最多丢一天的改动。
   - 写一个 `failover-hkspare.sh`，演练一次，要用户点头。
4. **以后要少丢一点**：SQLite 持续复制（Litestream 这类工具，把写入日志不停地传到对象存储或另一台机器），最多只丢几秒。要下载新工具，得用户同意；公测人多了再做。

不建议现在做双活或自动切换：SQLite 只能有一边写，两边都以为自己是主的话，数据会分叉；也没有云上的负载均衡，服务器的网络又不能动。
