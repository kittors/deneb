# M7 · 引擎安全审查（公测前）

> 引擎线，2026-11-10 01:0x，01:1x 补了要定的三件。范围：`engine/`、`cmd/denebd/`、`deploy/`。引擎在 Windows 上以 SYSTEM 跑（系统服务），在 Linux 上以 root 跑（denebd 包），macOS 搁置。按主会话列的五块逐条过：查了什么、结论、改了什么。代码都在工作区，没提交；没碰线上，也没碰测试设备。11-12 补了第 6 节（过滤器的模糊测试）、第 7 节（窗口拉起的引擎的日志）。

## 一句话结论

查出两处要紧的问题，都已改好：

- **Windows 服务拿用户目录当状态目录，能被普通用户借来提权**。这是 M6 时我自己建议的装法。
- **Windows 的命名管道能被别人抢先占用**。

另外补了三处加固：

- 一个对端能把流表、分片表填满，让这台设备连不了新连接；
- 撤销记录没核对就照着删；
- 正式版不能有测试接口，加了测试锁住。

拿不准的写在最后「没改、要定的」。

## 1. 本机接口：谁能连

**查了什么**：

- `engine/localapi/socket` 三个平台的监听和拨号；
- `-allow-uid`（macOS、Linux）、`-allow-user`（Windows）；
- 正式版里有哪些接口；
- 更新、停止、诊断这几个接口谁能调。

**结论**：

- **macOS、Linux 没问题**：
  - 套接字文件是 0600，放行的用户就 chown 给他；
  - 每个连接还会按对端 uid 再核一次（Linux 用 SO_PEERCRED，macOS 用 LOCAL_PEERCRED），只认 root、引擎自己的用户和放行的那一个；
  - 系统套接字在 `/var/run/deneb/`，目录只有 root 能写；
  - 假拓扑 M6 那轮验过：装包的用户能连，另一个用户被拒。
- **Windows 原来有一处要紧的问题：管道能被抢先占用**。
  - 系统服务和用户态引擎用同一个名字 `\\.\pipe\denebd`，而 Windows 上谁都能建任何名字的管道，客户端连到的是先建的那个。
  - 另一个普通用户可以抢在服务起来之前（开机、更新重启那几秒）建这个名字。窗口就会把请求发给他：登录、操作、粘贴进来的邀请链接，他还能回一个假的登录链接。
- 正式版里没有 `/v1/test/...`：测试接口只编进 denebtest 构建，正式版的 `TestHandler()` 是 nil。原来没有测试锁住这一点。
- 更新接口：只有 Windows 服务做，正式版不签名就回 `needs-install`，什么也不复制、不运行（见第 4 条）。
- 停止接口：只停用户态引擎，系统服务里的引擎拒绝。诊断包只给放行的人，就是这台设备的主人。

**改了什么**：

- Windows 系统服务改在 `\\.\pipe\ProtectedPrefix\Administrators\Deneb\denebd` 上听。这个前缀下只有管理员和 SYSTEM 能建管道，别人抢不了。
- 用户态引擎仍在 `\\.\pipe\denebd`，但建管道时把属主设成自己，只对自己和 SYSTEM 开放。
  - 客户端连上以后先核对（`checkOwnPipe`）：属主必须是自己，且没有放行别的用户。不对就不说话。做法和 Tailscale 一样。
  - 客户端会先找系统服务的管道，有人在听才用它，判断用的是不连上的 WaitNamedPipe，没有再找用户态的。
- 新加 `TestReleaseHasNoTestAPI`：不带 denebtest 编出来的引擎，`/v1/test/` 下的 shutdown、filter、inject、attack-route、paths、drops、http 全部回 404，引擎也没被停。
- Windows 部分三个平台都编得过，没在真机上跑过。

## 2. 隔离：过滤器有没有漏的路

**查了什么**：

- `engine/filter`，以及 `engine/datapath.go` 按网络图建策略的那段。逐条看了：
  - 局域网之间的隔离；
  - 分享的接收方不收别人发起的连接（NoInbound）；
  - 本机暂停、对端暂停；
  - 借道（进、出）；
  - 伪造来源；
  - 拆分包；
  - ICMP 差错；
  - IPv6、组播；
  - 换表时已有连接怎么切；
  - 拒绝。
- 另外看了流表、分片表满了会怎样。

**结论**：

- 隔离本身没找到漏洞：
  - 服务按"和这个对端共有、且不是 NoInbound 的局域网"放行；在 A 局域网开放的服务，B 局域网的人连不到；
  - 本机暂停的局域网，对端的包全部被丢；
  - 目的地址不是本机的进不来（transit-in），来源不是本机的出不去（transit-out），所以没法拿这台设备当路由器进它所在的局域网；
  - 来源由 WireGuard 按对端的 /32 核对，冒充不了别的对端；
  - 拆分包后面的几块只靠被放行过的第一块放行，TCP 太靠前的块直接丢；
  - ICMP 差错只在引用到本机和这个对端已有的流时才放；
  - IPv6 一律丢。
- **一个对端能让这台设备连不了新连接**（拒绝服务）：
  - 流表全机共 65536 条。任何能 ping 这台设备的对端（同一个局域网的成员都能），用不同的标识号 ping 6.5 万次（30 s 内，每秒约两千个），表就满了；
  - 之后谁的新连接都被丢，包括这台设备自己往外的；
  - 分片表（4096 条）也一样。
  - 另外，分片头原来记 30 s：持续发大的 UDP 包时，每秒超过约 140 个，表就自己满了，属于功能问题。
- 注释不符：`filter.Peer.Scopes` 的注释说"不含对端暂停的局域网"，实际代码是含的。M2 特意这么做：对端恢复时第一个包立刻能过，暂停由暂停的那一方自己守。

**改了什么**：

- 一个对端发起的流最多 4096 条（总数的 1/16），超出的丢弃，原因记作 `peer-flows-full`。别的对端和这台设备自己往外的连接不受影响。
- 一个对端的分片头最多占 1/4 的分片表。
- 分片头只记 5 s：同一个包的几块是一起到的，5 s 足够，表也不会被正常流量填满。
- 新测试：
  - `TestPeerCannotFillTheFlowTable`：一个对端 ping 满额度以后再 ping 被拒，别的对端、本机往外照样能连，过期以后又能 ping；
  - `TestPeerCannotFillTheFragmentTable`：分片头超额后，那个包的后几块被丢，别的对端照常，过期以后又能记。
- 改了那句注释，和实际做法一致。
- 假拓扑 Debian 13 内核模式（按名字 ping，含 1400、3000 字节的拆分包）用新过滤器又跑了一遍，结果见文末。

## 3. 密钥和状态

**查了什么**：

- 状态文件、撤销记录、日志的权限，三个平台都看了；
- 以 root 或 SYSTEM 跑的引擎会读写哪些目录；
- 日志会不会打出密钥或令牌；
- 诊断包（M6 已有测试）。

**结论**：

- 各平台的文件权限没问题：
  - macOS、Linux：状态目录 0700，文件 0600（`writeAtomic`、撤销记录、日志）；Linux 的 denebd 包状态在 `/var/lib/deneb`（0700，只有 root）。
  - Windows：用户态引擎的状态在用户自己的 `%LOCALAPPDATA%`；服务默认的 `%ProgramData%\Deneb` 是新建的，只给 SYSTEM 和管理员（M5）；`%ProgramFiles%\Deneb` 普通用户只能读。
- 日志：控制服务器的令牌只在内存里，不落盘，不打日志；WireGuard 的日志只打公钥的缩写；没找到打私钥、令牌的地方。
- 诊断包：私钥、公钥、登录和邀请链接都去掉了，M6 有端到端的测试。
- **要紧的一处（M6 我自己留下的）**：
  - M6 建议窗口这样装服务：`service install -state "%LOCALAPPDATA%\Deneb"`，为了不换设备身份。主会话测试机上也是这么装的。
  - 这样系统服务（SYSTEM）就在用户能写的目录里写文件：state.json 的临时文件和改名、网络图、撤销记录、锁文件、日志。
  - 用户（或者以他身份跑的任何程序）可以把这个目录换成联接点（junction），再借对象管理器的符号链接，让 SYSTEM 把文件写到他想要的地方，比如往 System32 放一个 DLL。这是 Windows 上常见的提权手法，不需要管理员权限。
  - 撤销记录也一样能被改：引擎崩溃后重启时，会以 SYSTEM 照记录去删 NRPT 规则。
  - macOS 的 M1 内核轮次（root 用用户的状态目录）在原理上也一样：记录能让 root 删一个内容可读的文件、或者删路由。
- Linux 的 root 守护进程用 `/var/lib/deneb`，不受影响。

**改了什么**：

- **Windows 服务的状态目录不许放在用户文件夹里**：`service install` 发现状态目录在 `C:\Users` 下就拒绝，并说明原因。
  - 设备身份改为装的时候带过去：`service install -import-state "%LOCALAPPDATA%\Deneb"`。安装程序（管理员）只读用户的 state.json 和 netmap.json，复制到服务自己的 `%ProgramData%\Deneb`（只有管理员能写）。服务从此只在那里读写。
  - 用户态引擎还在用那份状态（锁被占着）时拒绝带，提示先 `denebd shutdown`。服务已经有自己的身份时不再覆盖。
- **装服务的结果改写进注册表**：`HKLM\SOFTWARE\Deneb` 的 `ServiceInstall` 值，内容是"时间 ok"或"时间 原因"。用户能读，只有管理员能写，也就不会被重定向。原来写在用户目录的日志里，也是往用户能写的地方写。
  - 卸载时删掉这个键。
- **系统服务在跑时，Windows 上不再起用户态引擎**：服务的身份就是从这里带过去的，两个引擎同一个身份会互相打架。
- **撤销记录先核对，确认是 Deneb 写的才照着删**（三个平台，`Undo.check`）：
  - 网卡名只认 utun*、deneb*、Deneb；
  - 路由只认 IPv4 的地址段（至少 /8 那么具体），不认默认路由；
  - 解析文件只认 `/etc/resolver/` 下、内容由 Deneb 写的；
  - NRPT 规则只认 Deneb 那个固定的 GUID；
  - 不对的记录整份丢掉，什么也不做。
  - 新测试 `TestUndoRecordIsChecked`：几种伪造的记录都被拒，目录外一个内容对得上的文件没被删，Deneb 自己的三种记录照样通过。

## 4. 更新

**查了什么**：`cmd/denebd/update_windows.go`，以及 M6 真机验证的记录。

**结论**：

- 正式版（不签名）在复制任何东西之前就回 `needs-install`，所以没签名的文件进不来。
- 要是将来签了名：
  - 只认和正在跑的引擎同一个发布者，用 WinVerifyTrust 验链；
  - 版本按语义化版本比，降级拒绝（单测 `TestCompareVersions`）；
  - 先复制进只有管理员能写的 Program Files，再在那份上验签、问版本、改名换上，换的过程中文件改不了；
  - wintun.dll 只认 WireGuard 签的；
  - 重启由新文件起的短命进程做；
  - 真机上 updated、same、older、failed 四种都对过。
- **要注意的一点**：测试版（denebtest）的服务会接受没签名的文件，被放行的用户（可以不是管理员）就能让 SYSTEM 跑他的程序。测试版只给我们的测试机用，绝不能发出去。

**改了什么**：更新本身没改。测试版不出门的拦截见下一节第 2 条。

## 5. 中转和控制

**查了什么**：

- 控制服务器的 TLS；
- 中转站的 TLS；
- 令牌过期和设备被删时引擎怎么处理；
- 对端能往网络图里放进什么、能造成什么。

**结论**：

- **控制服务器**：
  - https 必须带公钥指纹，TLS 1.3 起步；
  - `VerifyConnection` 按叶子证书的公钥算 SHA-256，用常数时间比较；不对就断，不往下走；
  - 只钉公钥，所以服务器换证书、不换密钥，客户端不受影响。
- **中转站**：
  - 网络图里给了指纹就按指纹验，否则按系统根证书验；
  - 网络图本来就由控制服务器给，是信任的源头；
  - 中转站看不到 WireGuard 的内容，只能丢包或者延迟。
- **令牌**：
  - 控制令牌只在内存里，401 时用机器密钥签一次挑战，换新令牌，只重试一次；
  - 控制服务器说这台设备已登出（或已被删除）时，引擎清掉登录：过滤器换成全丢，对端、WireGuard、名字表都清空，网络图文件删掉。
- **对端能影响网络图里的哪些东西**：
  - 名字：完整域名由控制服务器按"名字.主人"分配，对端冒充不了别人家的设备；DNS 应答用的是查询里的名字，网络图里奇怪的名字也弄不崩引擎（没有会 panic 的 MustNewName）。
  - 地址：由控制服务器分配，WireGuard 按 /32 核对。
  - 声明的直连地址：对端可以声明任意 IP 和端口，这台设备就会往那里发 disco 探测包。这些包很小，按心跳和退避的节奏发，可以被拿来轻度扫描或者反射。
    - 对方回不出有效的回应：回应用 disco 密钥加密，没有密钥伪造不了，所以抢不走路径。
    - Tailscale 也是这样。没改。
  - 能力声明和服务列表：只影响怎么和它说话、界面怎么显示，不放行什么。
- 明文 http 的控制服务器：原来对任何地址都放行（只记一行警告）。网络图在路上能被换掉，就等于全盘失守。

**改了什么**：正式版拒绝明文 http 的控制服务器，回环地址除外（见下一节第 1 条）。

## 6. 过滤器的模糊测试（11-12）

**做了什么**：

- `engine/filter/fuzz_test.go`，用 Go 自带的 `testing.F`，共五个目标。
- 每个目标都拿一份另写的参考判断核对放不放，不只看崩不崩、读没读越界。参考判断自己读 IPv4 头，不用过滤器的 `Parse`。
- `FuzzFragments`（IPv4 分片）：同一个包整着送进一个过滤器，切开送进另一个，两个方向都试。下面这些都由输入决定：
  - 切多大、先后、重复；
  - 往前重叠 8 字节；
  - 加一片超过 65535 字节的；
  - 让首片晚到 fragHold 以后。
- `FuzzFragments` 的要求：
  - 整包不放的，一片也不放：目的不是本机的、来自非对端的、端口没开的、没人发起的回复；
  - TCP 落在头里（偏移小于 24）的片不放，超过 65535 字节的片也不放；
  - 像协议栈那样切的，整包放，每一片就都放。"像协议栈那样切"指：首片带完整的 L4 头，都在 fragHold 以内；进来时先到的片能暂存，出去时首片先发。
- `FuzzFragmentTable`（分片表满）：
  - 最多三个对端，每个灌两千以内的 ping 首片（ping 谁都能发），再灌一百多片永远等不到首片的后片；然后 lin 发一个两片的包。
  - 要求：没有哪个对端占到分片表的 1/4 以上，或暂存超过 64 片；lin 的包两片都进得来。
- `FuzzIPv6ExtensionHeaders`：
  - 逐跳、路由、分片、目的选项头随意串，最多 64 个；长度字段乱写，链在头中间截断，后面接 TCP、UDP、ICMPv6 或别的。
  - 要求：两个方向都按 `ipv6` 丢；流表、分片表、暂存都不变；也不回 reset。
  - 隧道里只走 IPv4，过滤器本来就丢所有 IPv6。这个目标确认不管怎么构造都一样。
- `FuzzICMPErrors`：
  - 两个方向。差错类型：不可达、超时、参数错误，另加重定向、时间戳。内层是 TCP、UDP、ICMP 或别的协议。来源、目的、端口、长度、IP 选项、分片位都由输入定。
  - 要求和参考判断每次都一样：只有引用本机和这个对端之间还活着的流才放。
  - 这些都不放：内层截断、内层是后片、差错套差错、引用别的对端的流、引用不存在的流、来自或发往非对端的。
- `FuzzPackets`：
  - 任意字节，两个方向。过滤器里先有几条流，还有 lin 一个刚开了头的分片包。
  - 要求放过的每个包参考判断都认：进来的目的是本机、来自对端，出去的反过来；后片要有 5 s 内放过的首片；L4 头完整；不超过 65535 字节。
  - 另外核对 `ResetFor` 造出的 reset 是回给这个包的。
- 种子取自单元测试里的包：TestFragments、TestFragmentedPing、TestEarlyFragments、TestICMPErrorsNeedAFlow、TestInbound。
- CI 照旧只跑 `go test`，也就是种子和 `testdata/fuzz/` 里的输入，不长跑。长跑的命令写在 `fuzz_test.go` 开头。

**跑了多久**（11-12，这台 MacBook Air，`-parallel=2`，每个目标 5 分钟，共 25 分钟）：

| 目标 | 时长 | 执行次数 | 结果 |
| --- | --- | --- | --- |
| FuzzFragments | 5 分钟，另有试跑几秒 | 1489 万 | 试跑时找到 1 处；改完再跑 5 分钟，没有 |
| FuzzPackets | 5 分钟，另有试跑几秒 | 2704 万 | 试跑时找到 1 处；改完再跑 5 分钟，没有 |
| FuzzICMPErrors | 5 分钟 | 2558 万 | 没有 |
| FuzzIPv6ExtensionHeaders | 5 分钟 | 1653 万 | 没有 |
| FuzzFragmentTable | 5 分钟 | 5.5 万（每次灌几千个包） | 没有 |

**找到、改了的**（都在 `engine/filter/packet.go` 的 `parse`）：

1. **超过 65535 字节的分片会放过去**：
   - 一个包的首片放过以后，同一个包偏移 65528 的一片照样放，进来、出去都是；
   - 拼起来就超过了 IP 包最大的 65535 字节，也就是老式的"死亡之 ping"。各系统的协议栈自己会丢，但过滤器不该放；
   - 现在"偏移加总长"超过 65535 的片直接丢，原因记 `fragment-too-long`，界限和 Linux 一样。
2. **不认识的协议的后片会被暂存**：
   - 协议号 48 之类的后片，过滤器会存 2 s 等它的首片。可这种协议的首片永远进不来，白占了那个对端的 64 个暂存位；
   - 这不算漏洞，是浪费；
   - 现在不认识的协议连后片一起丢，原因记 `protocol`。

## 7. 窗口拉起的引擎的日志（11-12）

用户 11-12 对 PRIVACY.md 里要定的几件回了"都按推荐"，这一件归引擎线。

- **原来**：macOS、Linux 上由窗口拉起的引擎（用户态），日志 `denebd.log` 只往后加，一连跑几天就一直长。
- **现在**：和 Windows 系统服务一样，超过 10 MB 就换。
  - 换的办法：把它挪成 `denebd.log.1`，原来的 `.1` 被替换；再开一个新的 `denebd.log`，只有这个用户能读写（0600）。
  - 启动时看一次大小，运行中每 30 s 再看一次。
  - 窗口拉起引擎时，用环境变量 `DENEB_LOG` 告诉它日志在哪。引擎先核对自己的 stderr 写的正是这个文件，才会去动它。
  - 换的时候用 dup2 把新文件接到 stdout、stderr 上。日志、库直接写到 stderr 的东西、崩溃时的输出，都接着写进新文件，一行不丢。
  - 换完，新日志的第一行写明：日志超过 10 MB，前面的在 `denebd.log.1`。
- **Windows**：系统服务启动时就会换（原来就有）。Windows 上由窗口拉起的引擎，也就是装网卡之前的那个，11-12 也补上了，规矩和 macOS、Linux 一样：
  - 难处：Go 在 Windows 上开文件不带 FILE_SHARE_DELETE，文件开着就改不了名。窗口把日志交给引擎当 stdout、stderr，引擎开着它的整个期间都改不了。
  - 现在窗口和引擎都用 `engine/logfile` 开日志。它在 Windows 上带 FILE_SHARE_DELETE，开着也能改名；别的平台照旧是 0600、只往后加。
  - 换的时候，先把开着的文件改名成 `.1`，再开新文件，然后把新文件交出去：
    - 用 SetStdHandle 换掉进程的标准输出、标准错误。Go 运行时崩溃时每次都会重新取标准错误，所以崩溃输出也进新文件；
    - os.Stdout、os.Stderr 和 log 也换成新文件；
    - 最后关掉旧句柄。
  - 新文件的权限跟着文件夹走：`%LOCALAPPDATA%` 只有这个用户、SYSTEM 和管理员能进。
  - 测试机 11-12 上午一直离线，所以把这几条测试放进了 CI 新加的 Windows 任务（GitHub 的 windows-latest，见 ci.md）。ef0486c 那一轮（run 43144978579）七个包都过，没有重跑：
    - `engine/logfile` 的 `TestRenameWhileOpen`：开着的日志能改名，连着两轮都行；
    - `cmd/denebd` 的 `TestRollLogWhileOpen`：开着的日志照样能换，换完接着写进新文件。
  - 还没做：在测试机上让窗口真的拉起引擎，把日志写过 10 MB，看它换。等测试机回来再做。
- **测试**：
  - `TestRollLog`：超了就换，没超不动；写日志的描述符接到新文件上，旧内容在 `.1` 里；新文件是 0600；
  - `TestRollLogWhileOpen`：日志在写的地方还开着（像引擎的 stdout、stderr），照样能换，换完接着写进新文件。在 Windows 上，这条就是改名这件事本身；
  - `logfile.TestRenameWhileOpen`：`logfile.Open` 开着的文件能改名，连着两轮，第二轮盖掉第一轮的 `.1`；
  - `TestRollLogOnlyItsOwn`：不是自己 stderr 的文件不碰。
  - 在这台 Mac 上真起了一个临时引擎（自己的状态目录和本机接口，只经中转，不开 SOCKS）：启动时 11 MB 的日志马上换了；运行中又写了 10.6 MB，29 s 后也换了，引擎照常在跑。

## 给客户端线的变化（Windows 装服务的流程）

旧流程是 `service install -state "%LOCALAPPDATA%\Deneb" -wait-lock 30s`，再 `/v1/shutdown`。改成：

1. `denebd shutdown`（或 `POST /v1/shutdown`）停掉自己的用户态引擎，等它退出；
2. 提权跑 `denebd.exe service install -import-state "%LOCALAPPDATA%\Deneb"`，弹一次 UAC；
3. 退出码不是 0：读 `HKLM\SOFTWARE\Deneb` 的 `ServiceInstall` 看原因，再把用户态引擎起回来；
4. 成功：照常连，客户端库会先找服务的受保护管道。

`needs-install` 时还是重跑第 2 步。服务已经有身份了，带过去这一步会自动跳过。
