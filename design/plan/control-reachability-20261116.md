# 控制服务器从国内直连连不上：怎么恢复，怎么不再犯（11-16）

> 方案。用户 11-16 定了：hk-spare 优先，Cloudflare 免费版兜底（§9）。hk-spare 的入口 11-16 19:13 已上线（next-round.md 第十四轮），Cloudflare 隧道还没建。公共中转站也接 Cloudflare 隧道，方案在 §10，等用户定。上线的每一步仍要用户点头。
> 排查记录（有真实地址）在共享笔记里，不进仓库。本文不写真实 IP、域名和家里的地址；两台香港机器照惯例叫 hk-155（控制服务器那台）、hk-spare（下载站那台）。

## 0. 一句话

hk-155 这个 IP 从国内直连被挡了 TCP，控制服务器本身没事。已装的设备只认这个 IP，所以服务器上怎么改都救不回它们，只能发新版；好在新版从 hk-spare 上的下载站送，下载站没被挡。

推荐分两步：
1. **马上做**：hk-spare 做第二个入口；新版带上一组入口、连不上自动换、把存下的旧地址迁过来；以后入口列表签名后放在下载站，换地址不用再发版。
2. **接着做**：控制服务器搬到一个不跑代理的 IP 上，不然换了 IP 还会被挡。

## 1. 发生了什么

- 11-16 12:10 起，从家里直连 hk-155，TCP 握手能过，之后服务器回来的 TCP 包全被丢掉。
  - 端口都一样：控制服务器的 47443、带正常域名的 443、纯 HTTP 的 80。
  - 同时 ping 一个包不丢。
  - 服务器负载、内存、控制服务器进程都正常，香港本地的机器连它也正常。
- 判断：整个 IP 被墙按 TCP 屏蔽了，可能性最大。hk-155 上跑着代理服务，这是常见的诱因（§4）。
- hk-spare（下载站、网页控制台）从家里直连是好的。
- 影响：
  - 家里的设备 12:10 起全部掉线，登录、上报、拿网络图都停了。
  - hk-155 上的中转站也连不上，设备只能改走 hk-spare 上的。
- 开了代理的用户现在也连不上：系统引擎连控制服务器固定走物理网卡，绕开了代理。引擎线在改"TLS 卡住就改走路由表"，改完这些用户能恢复。这台 Mac 走 Clash 的网卡连 hk-155，0.5 秒就通。
- 不走代理的普通用户受不受影响，正在请用户用手机流量、不开 VPN 试。结果只决定先做哪一步（§7），方案本身两种情况都适用。

## 2. 先弄清四件事

它们决定了哪些办法能用。

### 2.1 控制地址写死了，而且存进了设备

- 发行版的系统引擎内置一个控制地址 `https://<hk-155 的 IP>:47443` 和它的证书指纹（`cmd/denebd/control_default.go`）。
- 设备第一次登录后，把地址和指纹存进自己的状态，以后一直用存下的那个（`engine/engine.go`）。
- 控制服务器没有办法通知设备换地址：要先连得上才能说。

所以，**不发新版，服务器这边做什么都救不回已装的、直连的设备**，除非这个 IP 自己解封。中转站程序也一样：它的控制地址来自加入码，存在它自己的配置里。

### 2.2 新版送得到

- 桌面端从下载站查更新，每天在后台查一次，查到了在窗口里提示，用户点一下就装，系统引擎跟着桌面端一起换。
- 中转站程序也从下载站更新，每 6 小时自己查一次，自己换。
- 下载站在 hk-spare 上，没被挡，所以新版能送到已装的设备上。前提是 hk-spare 一直不被挡（§4）。
- Linux 服务器上的 .deb 不自动更新，要手动装。这类服务器大多在境外，一般不受影响。

### 2.3 设备核对的是证书指纹，所以换入口很便宜

设备核对的是控制服务器的证书指纹，不是 CA 签发的证书。只要入口把 TLS 原样转给控制服务器、不在中间解开，换哪个地址进来，指纹都对得上，不用换证书，也不用让用户重新登录。

### 2.4 网页控制台还能用

网页控制台在 hk-spare 上，由 hk-spare 去连控制服务器，这段是通的。所以被挡的用户现在还能用网页查看和管理。

## 3. 办法逐个看

| 办法 | 救谁 | 要新版吗 | 代价 | 多久 |
| --- | --- | --- | --- | --- |
| A. hk-spare 做第二个入口 | 装了新版的设备 | 要（设备得知道这个入口） | hk-spare 加一个小容器；控制服务器加一个监听口 | 半天 |
| B. 新版：一组入口、自动换、迁移 | 升级以后的所有设备，直连的和开代理的都救 | 要 | 引擎线、控制线各 1—2 天，发一版 | 2 天开发和测试，用户点更新后马上恢复 |
| C. 入口列表签名后放下载站 | 装了 B 以后的设备 | 和 B 一起发 | 1 天；签名和签更新包一样，由用户在终端运行 | 和 B 一起 |
| D. 控制服务器换一个干净的 IP | 配合 B、C，把新 IP 加进列表就行 | 有了 B、C 以后不用 | 一台小机器每月几十元；搬一次，停几分钟 | 半天到一天 |
| E. 把代理服务挪走 | 防止再被挡 | 不用 | 用户自己的代理要重新配 | 用户定 |
| F. CDN | 升级以后的设备 | 要，而且信任方式要改 | 3 天左右 | 一周左右 |
| G. 国内入口 | — | 要 | 备案几周，可能要买专线 | 不做 |
| H. 不动，等它解封 | 所有设备 | 不用 | 0 | 不知道 |

### A. hk-spare 做第二个入口

- **做法**：
  - 在 hk-spare 上起一个小转发程序（Docker，用一个新端口），把 TCP 原样转给 hk-155 的控制服务器，不解开 TLS。
  - 转发时加 PROXY 协议头，告诉控制服务器设备真实的地址。不加的话，控制服务器看到的全是 hk-spare 的地址：日志、按地址限流、中转站"拿请求来源当自己的地址"都会错。
  - 控制服务器加一个监听口，只接受从 hk-spare 来、带 PROXY 头的连接。
- **风险**：
  - hk-spare 也跑着代理，也可能被挡（§4）。
  - 多一跳，香港两台之间 4 毫秒左右，可以不计。
  - hk-spare 坏了，这个入口也就没了。
- **动线上的**：
  - hk-spare 多一个容器和一个端口，不动 nginx、防火墙、路由。
  - 控制服务器换一版，带上新的监听口。
- **光有 A 救不了已装的设备**，但它是 B 的备用入口，也能马上验证"换个 IP 进来就通"。

### B. 新版：一组入口、连不上自动换、迁移存下的地址

- **做法**：
  - 发行版内置的不再是一个地址，而是一组入口：hk-155 直连、hk-spare 转发，以后再加。它们都是同一个控制服务器、同一个指纹。
  - 设备按顺序试，连不上、或者 TLS 10 秒还没握完，就换下一个，并记住最近能用的那个。
  - 存下的地址如果是旧的内置地址，升级后换成这一组。自己部署控制服务器的人存的是自己的地址，不受影响。
  - 同一版带上引擎线的"TLS 卡住就改走路由表"，救开了代理的人。
  - 中转站程序同样改成一组入口。
- **风险**：
  - 入口都在香港这两台上，两台都被挡就都不通，所以还要 C 和 D。
  - 切换要测好，不能在入口之间来回跳。
  - 恢复多快取决于用户多快点更新：一天之内都能看到提示，但要用户自己点。
- **动线上的**：发一版，下载站放新包。控制服务器只有 A 那一处改动。

### C. 入口列表签名后放在下载站

- **做法**：
  - 下载站放一个签名的入口列表。设备每天取一次，连不上控制服务器时马上再取一次，核对签名后更新自己的入口。
  - 再放一两份备用：GitHub 发布页、国内对象存储的默认域名。下载站被挡时也能取到。
- **好处**：以后换 IP、加入口，改列表就行，不用发版。这次就是因为没有这一层，才只能发版。
- **风险**：
  - 列表必须签名，不然被人改了，就能把设备引向假的控制服务器。指纹核对也能挡住假服务器，算是双保险。
  - 取列表的地方本身也可能被挡，所以要放两三处。
- **动线上的**：下载站多一个文件；签名用发版的钥匙，由用户在终端运行。

### D. 控制服务器换一个干净的 IP

- **做法**：
  - 换一个不跑任何代理的 IP：新买一台香港或新加坡的小机器，或者让现在的服务商加一个 IP。
  - 控制服务器整个搬过去，数据库连同数据目录一起，停几分钟，沿用原来的钥匙，指纹不变。
  - 有了 B、C，把新 IP 加进入口列表就行。
- **风险**：
  - 新 IP 和代理放在一起，还会被挡。
  - 新 IP 可能以前被别人用过，已经在黑名单里。买之前先从国内测一下。
- **动线上的**：新机器；控制服务器搬家，要停几分钟，事先告诉用户。

### E. 把代理服务挪走

见 §4。

### F. CDN（比如 Cloudflare）

- **做法**：控制服务器放到 CDN 后面，用域名和正规证书。设备连这个入口时，改成核对 CA 证书。我们自己的指纹在这里用不上，因为 TLS 在 CDN 那里就解开了。
- **好处**：CDN 的 IP 很多人共用，很难整段挡。
- **代价和风险**：
  - Cloudflare 在国内，尤其是移动网络，又慢又丢包，高峰时常常用不了。
  - TLS 在 CDN 解开，CDN 能看到控制面的内容，比如设备的令牌和网络图。这和"只有我们能看到"的承诺冲突，真要做得写进 PRIVACY.md，并让用户知道。
  - 长轮询的超时要配合 CDN，比如免费版是 100 秒。
  - 控制服务器要从 CDN 加的头里取设备的真实地址。
  - 域名可能被 DNS 污染。
- **结论**：最多当最后一道备用，不做主入口。

### G. 国内入口

- 国内到香港这一段同样要过墙：香港的 IP 被挡了，国内服务器也连不上它，除非买专线，很贵。
- 用域名走 80、443 要备案，要几周。
- 在国内机器上转发到境外，有合规风险。
- **结论**：现在不做。

### H. 不动，等它解封

不花钱，但不知道要多久，几天到几个月都有可能，而且可能反复。不能指望。

## 4. 代理服务要不要挪走

要。这关系到换了 IP 还会不会再被挡。

- 被挡最常见的原因是这个 IP 上跑着代理。墙会主动探测、识别代理，认出以后挡整个 IP 的所有端口。这次的样子正是这样：整个 IP、所有端口。
- 两台香港机器上都跑着代理（sing-box）。排查时还看到，家里有一条到 hk-spare 443 的长连接一直在正常收发。所以 hk-spare 也有同样的风险，而下载站、网页控制台、第二个入口都在它上面。
- 只换 IP、不挪代理：新 IP 大概率还会被挡。
- 控制服务器、下载站、网页所在的 IP 上，最好只跑 Deneb，不跑代理。
- Deneb 自己的中转站也是长时间的 TLS 连接，里面全是加密数据，有被当成代理的可能。所以中转站最好也别和控制服务器用同一个 IP。
- 代理是用户自己在用的，挪不挪、挪到哪里由用户定。这台 Mac 上 Clash 的配置也只能由用户自己改。

## 5. 推荐

- **马上做 A + B + C**：hk-spare 做第二个入口。发一版新的，带上一组入口、自动切换、迁移存下的地址、引擎线的"改走路由表"，以及从下载站取签名的入口列表。
- **接着做 D + E**：控制服务器搬到一个只跑 Deneb 的新 IP，代理挪走，再把新 IP 加进入口列表。下载站和网页最好也搬到干净的 IP 上。
- **不做**：F 只当备用，G、H 不做。
- **新版发出以前**：已装的直连设备没法恢复。能做的是告诉用户：网页控制台还能用，设备掉线是线路的问题，不是他们的设备坏了。

## 6. 第一步

以下要用户点头。

1. **A**：在 hk-spare 起转发入口：新端口，只转 TCP，不解开 TLS，带 PROXY 头。控制服务器换一个带 PROXY 监听口的版本。然后从家里直连验证 TLS 能通。大约半天。
   - 要动线上的：hk-spare 一个新容器和端口，控制服务器换版。
2. **同时开发 B + C**，一起发版：
   - 引擎线：设备端的入口列表、切换、迁移、改走路由表；
   - 控制线：PROXY 监听口、入口列表的签名工具和下载站上的文件、中转站程序的入口列表；
   - 客户端线：设置里"连接的服务器"显示当前用的是哪个入口。
3. **D、E**：等用户决定代理怎么挪，再定新机器。

## 7. 手机流量的结果怎么改先后

- **手机流量也连不上**：全国直连的用户都受影响。A、B、C 立刻做，尽快发版，D、E 紧接着做。
- **手机流量能连上**：可能只是家里这条线路，或者这家运营商的这一段。B、C 照样做，以后换地址不用发版，值得做；A 可以缓一缓。家里的线路继续观察，必要时找运营商。

## 8. 顺手要改的

- **公开仓库里写死了控制服务器的真实地址**：在 `cmd/denebd/control_default.go`、`cmd/deneb/main.go`、`deploy/web/site.example.env`、`control/server.go` 和 `cmd/deneb-control/main.go` 的注释和报错里。这违反了 AGENTS.md 的规矩，也让人一搜就知道这个 IP 是 Deneb 的控制服务器。B 里把入口改成打包时从部署配置写进去，和下载站地址一样，顺手把这些都清掉。地址已经留在历史里了，以后的新地址不要再进仓库。
- **中转站加入码里的控制地址**：加入码里带的也是这个地址。新版的加入码要能带一组入口，或者只带控制服务器的名字，由程序从入口列表里找。

## 9. 用户 11-16 定了：hk-spare 优先，Cloudflare 兜底

用户先说"用 hk-spare 也行"，又说"如果可以用 CF 的免费方案是最好了"。问过 Cloudflare 能看到内容这一点以后，定为：**新版依次试 hk-155、hk-spare、Cloudflare**。前两个照旧核对我们自己的指纹，内容只有我们看得到；两个都连不上才走 Cloudflare，那时它看得到内容，PRIVACY.md 已写明。全部免费。

这一来，§3 里的 F 从"最后的备用"变成第三个入口。

### 9.1 Cloudflare 免费版行不行（11-16 从家里直连实测）

- 通：4 次都是 200。走的是美国西海岸的机房（洛杉矶、圣何塞），TLS 握手 0.4—1.6 秒，往返约 210 毫秒，ping 10 次丢 1 次。控制面流量很小，这个速度够用。
- 长连接：控制服务器每 15 秒发一次保活，Cloudflare 的空闲超时是 100 秒，不会被断。
- 免费版不能把 TLS 原样转发（那是付费的 Spectrum），所以 TLS 一定在 Cloudflare 解开。
- 不开新的公网端口：用 Cloudflare Tunnel。控制服务器那台主动连出去，Cloudflare 的请求顺着这条隧道进来。

### 9.2 服务器这边已经做好的（本机测过，没上线）

- **控制服务器**多两个监听口：
  - `-front-listen :47444`、`-front-from <hk-spare 的地址>`：给 hk-spare 上的转发用。只收那台发来的连接，开头先读 PROXY 头拿到设备的真实地址，后面照常是 TLS，证书和指纹都不变。
  - `-tunnel-listen 127.0.0.1:47450`：给同一台机器上的 cloudflared 用，明文 HTTP，只收本机连接，设备的地址只认 `CF-Connecting-IP`。
- **`cmd/deneb-front`**：转发程序，放在 hk-spare 上。TCP 原样转给控制服务器的 `-front-listen`，前面加 PROXY 头，不记设备的地址。部署脚本在 `deploy/front/`，照看门狗的做法：空镜像里只放一个程序，用主机网络，不加任何防火墙规则；部署前后各打印一遍容器和监听端口，好对比。
- **测试**：
  - `control/front`：PROXY 头（v2、v1、LOCAL、各种坏头），经转发的 TLS 和 HTTP/2，不是转发的机器直接关掉，隧道口。
  - `cmd/deneb-front`：数据原样来回，控制服务器不在时设备的连接会关掉。
  - 都加 `-race` 跑过。
  - 本机端到端：经过 `deneb-front` 拿到的公钥指纹和直连一样，`/healthz` 回 200（HTTP/2）；不带 PROXY 头直连转发口被拒；隧道口带 `CF-Connecting-IP` 回 200、不带回 403。
- **两台服务器的防火墙**（只读看过）：进站默认都是放行，没有 ufw、firewalld，所以新端口不用改防火墙。

### 9.3 设备这边（引擎线）

入口列表的样子，内置在发行版里（打包时从部署配置写进去，不进仓库），以后也放到下载站（§3 C）：

```json
{
  "version": 1,
  "entrances": [
    {"url": "https://<控制服务器的地址>:47443", "pin": "sha256:…"},
    {"url": "https://<hk-spare 的地址>:47443", "pin": "sha256:…"},
    {"url": "https://control.deneb.app"}
  ]
}
```

- **核对**：
  - 有 `pin` 的入口，核对控制服务器的指纹，和现在一样，不看证书上的名字。
  - 没有 `pin` 的入口（Cloudflare），按系统的根证书和网址里的域名核对。
- **顺序**：按列表的顺序试。连不上、或者 TLS 10 秒没握完，就换下一个。下次从上次能用的那个开始，但每隔一段时间回头试一下前面的，能直连了就不再走 Cloudflare。
- **迁移**：设备存下的地址如果是旧的内置地址，升级后换成这一组。自己部署控制服务器的人存的是自己的地址，不动。
- **开了代理的人**：同一版带上"TLS 卡住就改走路由表"。
- **签名的列表**（§3 C）：`version` 更大、签名对得上才换。签名照中转站更新清单的做法，用发版的钥匙。

### 9.4 上线的步骤

每一步都要用户点头，由主会话安排。

1. **先换网页版，再换控制服务器**：
   - 网页版（hk-spare 上的 deneb-web）先换到带 `/device-login` 的版本（§9.5）；
   - 再换 hk-155 上的控制服务器，加 `-front-listen :47444 -front-from <hk-spare 的地址>`，不改防火墙。
   - 顺序不能反：新的控制服务器发出的浏览器登录链接指向网页版的 `/device-login`，网页版还是旧的就打不开。
2. **hk-spare 起转发**：写好 `deploy/front/front.hk-spare.env`（`LISTEN=:47443`、`DENEB_FRONT_TO=<hk-155 的地址>:47444`，不进仓库），运行 `HOST=hk-spare deploy/front/deploy.sh`。hk-spare 上 47443 端口空着（只读看过）。
3. **从家里直连验证**：经 hk-spare 的 47443 拿到的指纹和控制服务器的一样，`/healthz` 回 200。
4. **Cloudflare**：
   1. 用户在 Cloudflare 后台（Zero Trust → Networks → Tunnels）新建一个隧道，免费，选 Docker；拿到的令牌放到 hk-155 上的一个文件里（0600），不进仓库，也不贴到聊天里。
   2. 隧道的公开地址填用户域名下的一个子域名，服务填 `http://127.0.0.1:47450`。
   3. hk-155 上跑 cloudflared，用主机网络，只往外连；控制服务器加 `-tunnel-listen 127.0.0.1:47450`。
   4. 从家里直连验证：经 Cloudflare 的子域名访问 `/healthz` 回 200。
5. **发新版**：引擎线做 §9.3，新版放到下载站。设备一天内会看到更新提示，点了更新就恢复。

第 1—3 步大约半天，第 4 步要用户在 Cloudflare 后台操作一次，第 5 步看引擎线。

### 9.5 在浏览器里登录设备的页面，挂到网页版下（引擎线 11-16 提的）

- **原来的问题**：设备在浏览器里登录（比如服务器上的 `deneb login`）时，链接是控制服务器自己的 `/login?c=`，按 `PublicURL` 写，指向 hk-155。
  - 被挡的用户打不开。
  - 控制服务器用的是自签证书，直连的用户也会看到"证书不受信任"。
  - 设备端把链接改成正在用的入口，能解决打不开，解决不了证书：经 hk-spare 转发，还是同一张自签证书。
- **`LoginURL` 不能改**：桌面端窗口里的邮箱登录（`client/signin.go`）从 `LoginURL` 里取地址，只认控制服务器的各个入口，按指纹往那里交表单。`LoginURL` 换成网页版的地址，窗口就认不出，只能退回浏览器。所以 `LoginURL` 仍指向控制服务器，设备端照旧把它改成正在用的入口。
- **改成另给一个 `BrowserURL`**：登录状态里新加一个字段，专门给浏览器用。设了 `-web-url` 时，它指向网页版的 `/device-login?c=`：网页版有正式证书，放在 hk-spare 上，被挡的用户也打得开。没设时，它和 `LoginURL` 一样。旧的设备不认识它，照旧用 `LoginURL`。
  - deneb-web 把 `/device-login`（打开页面，以及下面的 `/email`、`/code` 两个表单）原样转给控制服务器，页面还是控制服务器的那几页。
  - 表单交到页面所在的路径下。
  - 跨站检查把网页版的来源当成可信的。
- **旧链接照旧能用**：控制服务器自己地址上的 `/login?c=` 不变。
- **设备端要做的（引擎线、客户端线）**：要把人送去浏览器的地方改用 `BrowserURL`，没有它再用 `LoginURL`。包括 `deneb login` 打印的链接、窗口里"在浏览器里登录"的按钮。引擎要把这个字段带到本机接口的状态里。
- **测试**：
  - `control` 的 `TestDeviceLoginUnderWeb`：`LoginURL` 仍指向控制服务器，`BrowserURL` 在网页版下，两个是同一个登录码；网页版下的页面表单交到 `/device-login/…`；网页版来源的表单收，别的站来的回 403；控制服务器自己地址上的页面照旧交到 `/login/…`。
  - 没设网页版时，`BrowserURL` 和 `LoginURL` 一样（`server_test.go` 的登录）。
  - `cmd/deneb-web` 的 `TestDeviceLoginPassedOn`：页面和表单连同 Origin 原样转给控制服务器。

## 10. 公共中转站也接 Cloudflare 隧道（用户 11-16："公共中转都用 cf隧道"）

> 方案，等用户定 §10.4 的甲、乙。

### 10.1 现在

- 公共中转站"香港"在 hk-155 上，和控制服务器同一个 IP。它是 Tailscale 的 DERP：设备用 TLS 长连接连它的 47445 端口，核对它自签证书的指纹。
- 12:10 hk-155 被挡以后，它也连不上，设备只能改走 hk-spare 上的 `hk`。
- 不在这次范围里的：
  - `hk` 是用户自己的 derper，不是 Deneb 的程序，配置不归我们改（implementation.md）。
  - hk-spare 上的 Deneb 中转站是"我的服务器"，不是公共的。

### 10.2 走得通吗

- **要换成 WebSocket**：免费的隧道只转 HTTP 和 WebSocket。DERP 平时把 HTTP 升级成它自己的协议，Cloudflare 不认这种升级。
- **设备这边要自己写这条路**：Tailscale 的 DERP 客户端只在浏览器里用 WebSocket。macOS 上要加特别的编译标记，而且是全局开关；Windows 上没有。做法：
  1. 用 WebSocket 连隧道的域名，按系统的根证书核对；
  2. 连上以后，在里面照常说 DERP。
- **中转站这边**：多一个只收本机连接的口（`-tunnel-listen 127.0.0.1:47451`），给同一台机器上的 cloudflared 用。
  - 进来以后和直连的一样：准入问控制服务器、计流量、限速都照旧。
  - 设备的地址从 `CF-Connecting-IP` 取，准入和日志看到的和直连时一样。不带这个头的连接回 403，和控制服务器的隧道口一样。
- **一条隧道就够**：控制服务器和"香港"在同一台机器上。隧道里配两个公开地址：
  - 控制服务器的 → `http://127.0.0.1:47450`；
  - 中转站的 → `http://127.0.0.1:47451`。
- **STUN 走不了**：它是 UDP。它只帮设备找自己的外网地址，没有它照样能经中转站连。
- **长连接不会被断**：DERP 每 60 秒发一次保活，Cloudflare 空闲 100 秒才断。Cloudflare 自己换版时会断开，设备会自动重连。

### 10.3 Cloudflare 看得到什么

- **看不到内容**：中转站里转的是设备之间加密好的包，钥匙只在两端的设备上。
- **看得到**：
  - 设备的 IP、什么时候连；
  - 谁发给谁，只是设备的公钥，不是名字；
  - 传了多少。
- 直连时，这些只有我们看得到。PRIVACY.md 照这个写，和控制服务器走 Cloudflare 的那段放在一起。

### 10.4 平时走哪条：两种做法，等用户定

**甲：先直连，连不上再走 Cloudflare（推荐）**

- 平时和现在一样快。
- 规矩和控制服务器的入口一样（§9.3）：
  - 3 秒连不上，或者 TCP 通了、TLS 10 秒没握完（12:10 那种），就换 Cloudflare；
  - 下次从上次能用的那条开始，每 30 分钟回头试一次直连。
- 代价：中转站的 IP 上照旧有直连的流量，可能被当成代理挡掉，还会连累同一个 IP 上的控制服务器（§4）。
  - 挡了也能自动接上：控制服务器有 hk-spare 和 Cloudflare 两个后备，中转站有 Cloudflare。

**乙：只走 Cloudflare**

- 好处：新版的设备不再直连中转站的 IP，这个 IP 上就只剩控制服务器自己的流量，更不容易被挡。旧版照旧直连，直到升级。
- 代价：
  - **慢**：国内经 Cloudflare 免费版走美国西海岸，往返约 210 毫秒，有丢包，高峰时常常用不了（§3 F、§9.1）。中转站本来就是直连不通时才用，再慢一截，远程桌面、视频通话会卡。
  - **可能被限**：Cloudflare 的条款写明，免费版不能拿来大量传视频和大文件，否则可能限速或停用。所有中转的流量都过它，量会比甲大得多。
  - 所有经中转站的连线，Cloudflare 都看得到 §10.3 的那些。

推荐甲：速度不变，挡了能自动接上，经 Cloudflare 的只是被挡的那一部分。以后想让中转站的 IP 更干净，办法是给它单独一个 IP（§4），而不是全部走 Cloudflare。

### 10.5 要改的

- **网络图**（`proto.Relay`）：多一个 `Tunnel`，填隧道的域名，比如 `relay.deneb.app`。旧版的设备不认识它，照旧直连。
- **中转站程序**（控制线）：
  - 加 `-tunnel-listen`、`-tunnel-host`；
  - 把隧道的域名随自己的信息报给控制服务器，控制服务器写进网络图；
  - 只给公共中转站开。
- **引擎**（引擎线）：
  - 每个中转站有两条路，按 §10.4 定下的规矩选；
  - 开了代理的人，和控制服务器的 Cloudflare 入口一样处理；
  - 正在用哪条写进诊断包。
- **窗口**：不变。中转站卡片照旧写"公共中转站"，不提 Cloudflare。
- **部署**：
  - hk-155 上跑 cloudflared：Docker，主机网络，只往外连，令牌放在 0600 的文件里；
  - 中转站加 `-tunnel-listen 127.0.0.1:47451 -tunnel-host <域名>`；
  - 控制服务器加 `-tunnel-listen 127.0.0.1:47450`。
- **测试**：本机起一个只认 WebSocket 的假"Cloudflare"，把中转站和引擎两头接起来。直连那条分别给一个连不上的地址、一个 TLS 卡住的地址，看会不会换、会不会换回来。

### 10.6 上线的步骤

每一步都要用户点头。

1. 用户定甲或乙。
2. 控制线、引擎线照 §10.5 改，CI 全绿。
3. 用户在 Cloudflare 后台建隧道（§9.4 第 4 步），配上 §10.2 的两个公开地址，令牌放到 hk-155 上的文件里。
4. 上线 cloudflared、控制服务器、"香港"中转站；从家里经两个域名验证。
5. 打 rc.4 真机测：
   - 用启动时带的测试开关（像 `DENEB_UPDATE_SOURCE` 那样）让"香港"的直连故意连不上，看经 Cloudflare 能不能用，不动这台 Mac 的网络；
   - 同一轮测入口切换，和引擎换版时窗口不闪（m7/engine-restart-offline.md 的 C）。
6. 发 0.1.9。
